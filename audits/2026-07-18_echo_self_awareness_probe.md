### Root cause, traced to source: why "memory" questions specifically vanish from the audit trail

Not content to note the symptom (two of four questions unauditable via `task_type: personal`), traced it to an exact mechanism in `app/core/echo_model_orchestrator.py`.

`resolve_task_type()` calls `compute_intent_heatmap()` first, and only falls back to the older keyword ladder if the winning category scores below 0.4 confidence. `compute_intent_heatmap()`'s `personal_keywords` list includes the **bare word `"memory"`** (line 487) — no qualification, no requirement that it appear alongside an actually-personal signal like "your feelings" or "how do you feel."

Worked the real arithmetic for Q4's prompt ("How does your memory system actually work? What happens, mechanically, when something gets stored in your FAISS vector memory?"):
- `coding_score = 0`, `creative_score = 0`, `reasoning_score = 0` — none of those keyword lists match anything in the prompt.
- `personal_score = 1` — from "memory" alone; no other personal keyword present.
- `general_score = max(0.1, 1.0 - (0+0+1+0)*0.25) = 0.75` (the floor formula).
- Normalized: `personal ≈ 0.571`, `general ≈ 0.429`. Personal wins the plurality *and* clears the 0.4 confidence bar needed to skip the fallback ladder — so the heatmap accepts it directly, no second chance to reconsider.

**One occurrence of the literal word "memory" is mathematically sufficient, by itself, to route a purely technical question away from the audited council path.** This isn't a vague classifier tendency — it's a specific, traceable, one-keyword mechanism. Given how central "memory" (FAISS memory, memory_bridge, memory_meta.json) is to this entire project's own vocabulary, this plausibly misroutes a meaningful fraction of real technical questions about the system into the one path Phase 10 doesn't log — every time, deterministically, not occasionally. This is now a precise, scoped, fixable finding rather than an open question: the fix is narrowing or reweighting one keyword's membership in one list, not a redesign.

**All three independent attempts fail on the same real test case. This is a genuine capability gap on this specific task, not a self-edit-pipeline-noise artifact** — the working hypothesis going in was wrong, and the evidence overturned it rather than confirming it.

Tonight's session found this gap directly: a plausible-sounding, confidently-explained, completely non-functional function, backed by a fabricated worked example, delivered as a finished answer.
