Determine whether v1.2's byte-identical CONTROL/EXPERIENCE result reflects a real absence of

## 4. Generation Architecture Examined

`v1_2_clean_transfer.py`'s `generate()` calls `echo_model_orchestrator.echo_query(prompt,
task_type="coding", source="autonomous", trace_id=None)` — no `temperature` argument passed (defaults
to `None`). For `task_type="coding"` this is **not** a `DIRECT_ECHO_TASKS` bypass — it routes through
`river_deliberation.deliberate_and_learn()`'s real multi-councillor path: `_select_council()` (reads
`model_task_stats`, which `neutralize_river_brain_writes()` freezes for this whole session — no
`.learn()` call ever fires, so the ranking cannot change between calls), then per-councillor
`_ollama_query()` calls at a temperature computed by `_jittered_temperature(base=None, index, count)`
— **read directly**: `center = 0.7` (the module's own fallback constant, since `base is None`), then a
small, purely index-based offset — a **deterministic function of council seat position**, not a random
draw. Confirmed via direct grep across `app/ollama_handler.py` and `river_deliberation.py`: **no
`seed` parameter is set anywhere in this pipeline, ever.** `_options["temperature"]` in
`ollama_handler.py` is set explicitly whenever `temperature is not None` — and `_jittered_temperature()`
never returns `None`, so a real, specific numeric temperature genuinely reaches every real Ollama call.

Fallback-selection mechanism, read directly (`select_best_fallback_candidate()`, line 942): when
synthesis is rejected (here, because it dropped the agreed-upon `EventTracker` definition — confirmed
live, both runs, identical warning text), the function deterministically prefers a candidate whose code
parses, tie-broken by `max(pool, key=len)` — a pure function of the real per-councillor response text,
with no randomness of its own.

## 14. Determinism/Cache/Fallback Analysis

Three real, evidence-grounded contributing factors, chained:

1. **Frozen council composition.** `neutralize_river_brain_writes()` (active for this entire experiment
   session, confirmed) means `model_task_stats` never changes between CONTROL-A and CONTROL-B, so
   `_select_council()`'s ranking — and therefore the exact set and order of councillor models — is
   identical both times. This alone is necessary but not sufficient for byte-identical text.
2. **Deterministic per-seat temperature.** `_jittered_temperature()` computes a fixed value from
   `(index, count)` alone, with `base=None → 0.7` — the same real temperature value reaches the same
   councillor seat both times. Necessary but still not sufficient on its own — a real temperature > 0
   with genuine sampling should still vary token-by-token without a fixed seed.
3. **The actual per-councillor Ollama responses were byte-identical, not merely similar.** This is the
   load-bearing, most consequential finding: with (1) and (2) held constant and **no seed parameter
   ever set anywhere in this codebase's Ollama call path** (confirmed by direct, targeted grep — a real,
   checkable negative, not an assumption), the underlying Ollama/llama.cpp backend still produced
   identical token streams across two fully independent HTTP calls. **The most parsimonious explanation
   consistent with this evidence is that the serving backend defaults to some fixed decoding behavior
   (e.g., an implicit fixed seed) when none is explicitly randomized or specified** — this report does
   not independently verify Ollama's internal default-seed behavior against its own source/documentation
   (out of scope for this pass, flagged as unresolved at that specific layer), but the *observable
   consequence* — real, same-model, same-temperature, same-prompt calls converging byte-for-byte,
   twice, live — is directly established here, not inferred.

**Caching/memoization**: no evidence of a prompt-hash cache found in the real call path traced (`
_ollama_query()` → `stream_query_ollama()` makes a genuine new streaming HTTP request every call, read
directly) — the repeated-identical-output phenomenon is consistent with backend-level decoding
determinism, not an application-level cache short-circuiting the call entirely (a genuine cache would
also not explain two separately-logged, separately-timed real streaming calls with distinct wall-clock
durations, 38.95s vs. 36.79s — different timings but identical content is itself evidence against a
naive response-reuse cache, which would typically also short-circuit the elapsed time).

## 15. Alternative Explanations Considered and Ruled Out

- **Prompt-level caching**: ruled out by distinct elapsed times (§14) — a cache hit would not take
  ~37-39 real seconds twice.
- **RiverBrain state drift causing a different council**: ruled out directly — `river_brain.pkl`'s
  mtime never moved (§3), confirming the frozen state this whole diagnostic depends on actually held.
- **Two different candidates coincidentally tying on length**: ruled out by the raw-response-level byte
  identity (§10) — the underlying per-model outputs were identical, not merely equally-ranked by the
  tie-break rule.

## 16. Implications for v1.2

v1.2's RED verdict stands, unmodified, per this mission's own explicit instruction. What this pass adds:
**the absence of variation in v1.2 is not surprising or uniquely diagnostic of "the model ignored the
lesson" — this exact real production pathway, under the exact isolation conditions both experiments
share (frozen RiverBrain state, no seed anywhere), produces deterministic output even with zero prompt
difference at all.** This means v1.2's specific result (different prompts → identical output) is now
best read as: *whatever token-level divergence a one-sentence appended lesson might have caused in
principle, it did not survive whichever deterministic decoding process governs this backend under these
conditions, for this task.* This is a more precise, more mechanistically-grounded restatement of RED,
not a weaker one — it sharpens *why* no variation was observed, without asserting that a differently
configured pipeline (real sampling variance restored) would necessarily behave the same way.

## 17. Highest-Value Remaining Hypothesis

Ranked candidates, tied to the evidence actually gathered across this whole experimental series:

1. **(Highest-ranked)** The generation pipeline's deterministic decoding (§14) makes any single-trial
   prompt-content comparison under these isolation conditions structurally unable to detect a real,
   smaller lesson effect that would only appear under genuine sampling variance — not because the model
   can't use lessons, but because this specific experimental setup (frozen RiverBrain + no seed
   randomization) accidentally also froze the decoding process itself.
2. Council-synthesis's rejection-and-fallback path (both CONTROL-A and CONTROL-B, and v1.2's own
   CONTROL/EXPERIENCE, all hit this exact path) discards the synthesis step entirely and returns a raw
   single-councillor candidate — meaning **whatever cross-councillor integration synthesis might
   provide as a channel for lesson-sensitivity never actually ran** in any of these trials. This is a
   second, independent way the pipeline's own real behavior (not model incapability) could suppress
   lesson-sensitivity specifically for this task shape.
3. (Lower-ranked, not newly supported by this pass) Explicit textual lessons may simply not be an
   effective substrate for this model/task combination — still possible, but this pass's findings mean
   hypotheses 1 and 2 must be ruled out first before concluding this.

## 18. Single Recommended Next Experiment

**Re-run v1.2's exact CONTROL/EXPERIENCE comparison with one change: pass an explicit, varying seed (or
otherwise force genuine sampling variance) to the underlying Ollama calls, and separately verify whether
the trial hits the synthesis-rejection fallback path or genuine synthesis.** Hypothesis: if CONTROL and
EXPERIENCE now diverge in content even without the lesson present (i.e., repeat this exact
same-prompt-twice diagnostic with real seed variation and confirm CONTROL-A ≠ CONTROL-B), that confirms
sampling variance can be restored, making a subsequent real CONTROL-vs-EXPERIENCE comparison
meaningful for the first time. Success criterion: CONTROL-A ≠ CONTROL-B under seed variation (proving
the pipeline *can* vary) — failure/stop criterion: if seed variation still fails to produce divergence,
this points at a deeper backend-level issue outside this pipeline's own code, and the experimental
thread should pause pending that separate investigation rather than continue consuming real trials
against a decoding process that cannot vary.

## 19. Should This Thread Continue?

**Conditionally yes, but not with the current isolation conditions unmodified.** The evidence in this
pass identifies a concrete, previously-unknown confound (deterministic decoding under the exact
conditions every experiment in this series has used) that must be addressed before another
CONTROL-vs-EXPERIENCE comparison can be trusted to mean what it appears to mean. This is not "the
learning thread is dead" — it is "the measurement instrument itself needs one specific, cheap fix before
the next measurement is trustworthy."

## 20. Final Verdict

**DIAGNOSTIC NEGATIVE** — independent CONTROL calls deterministically converge (byte-identical, both
extracted code and raw response, confirmed directly); the pipeline's own real, current configuration
(frozen RiverBrain state + no seed randomization, both already established as necessary for the prior
experiments' safety/reproducibility goals) is sufficient to explain the identical output, independent of
any question about the model's capacity to use a lesson.

## §15 Answers

**What is the strongest thing we now know about why Echo is not learning from this lesson?** We do not
yet know that she isn't — we know that the specific instrument used to test it (this exact pipeline,
under RiverBrain-frozen, no-seed conditions) cannot currently distinguish "the lesson had no effect"
from "nothing could have had any effect, because decoding itself doesn't vary here." The v1.2 RED result
remains the best current evidence, but its precision is now understood to be bounded by this mechanism,
not merely by sample size.

**What is the cheapest experiment that could most efficiently prove us wrong?** §18's seed-variation
same-prompt-twice check — a single, cheap, same-prompt repeat (no lesson involved at all) that directly
tests whether this pipeline can produce different output under otherwise-identical conditions once
sampling variance is deliberately restored. If it can, the next real CONTROL-vs-EXPERIENCE run becomes
trustworthy for the first time in this whole series. If it can't, the problem is upstream of anything
this experimental series' own design can fix.
