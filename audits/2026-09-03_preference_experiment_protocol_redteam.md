# Preference Experiment — Protocol Red-Team

Adversarial review performed before freezing
`audits/2026-09-03_preference_experiment_preregistered_protocol.md`. Every
attack below was actually attempted against the real implementation
(`app/experiments/preference_provenance/`), not reasoned about in the
abstract — several were caught live, mid-pass, by actually running
`scripts/calibrate_preference_provenance_harness.py` against the real
code and watching it fail in ways that revealed genuine design problems,
not merely by inspection. Classification vocabulary, per the mission:
**FIXED** / **CONTROLLED** / **ACCEPTED_LIMITATION** / **PROTOCOL_INVALIDATING**.

No attack in this document reached `PROTOCOL_INVALIDATING`. Several
reached findings serious enough that, had they gone unfixed, they would
have invalidated any future result — those are marked explicitly below.

## The 20 named attacks

| # | Attack | What was actually done | Classification | Notes |
|---|---|---|---|---|
| 1 | Can the prompt reveal the preference? | Built `leakage.py`, wired into `run_trial()` as a hard stop (`HiddenStateLeakageError`) for every hidden-state trial. Verified directly: a task description containing the candidate's own text is refused before any responder call. | **FIXED** (literal/near-literal) / **ACCEPTED_LIMITATION** (arbitrary paraphrase — stated in `leakage.py`'s own module docstring, not overclaimed) | This is the single most consequential fix in this pass — the prior implementation explicitly documented this as caller-responsibility-only, with zero enforcement. |
| 2 | Can option ordering reveal the preference? | `randomize_label_mapping()` re-randomizes every trial (already existed); this pass added a dedicated fixed-order invariance check (both in the calibration script and as a regression test) proving the measured rate is statistically similar under both possible fixed orderings. | **CONTROLLED** | Verified empirically this pass: rate(A-first)=0.78 vs rate(B-first)=0.72 — close enough to support invariance, not identical (expected, since these are still stochastic samples, not the same underlying draws). |
| 3 | Can memory reveal the preference? | For `MockResponder`: not applicable (no memory system exists). For a real `EchoResponder` trial: `echo_query()`'s internal FAISS retrieval could, in principle, surface a prior trial's own logged content in a later trial. Not fixed — fixing it would require modifying production `echo_query()`/`memory_bridge.py`, out of scope for this pass and forbidden by the mission's safety boundary. | **ACCEPTED_LIMITATION** | Mitigated, not solved: `EchoResponder` now requires `acknowledge_contamination_risk=True` (attack #23 below) specifically so this can never be invoked by accident. The pre-registered protocol requires this be explicitly addressed (e.g. via a dedicated conversation/session per trial, or a memory-exclusion tag) before any real trial batch runs. |
| 4 | Can task selection reveal the preference? | Built `task_bank.py`: 11 domain-neutral templates, none referencing any specific candidate content, seeded/reproducible generation. | **CONTROLLED** | Verified: same seed reproduces the identical sequence; fingerprint recorded so a later re-run can detect if the bank itself changed. |
| 5 | Can metadata reveal the condition to the model? | Checked structurally: `Responder.respond()`'s signature never receives `condition`, `candidate_id`, or any lifecycle status — only `task_description`, `label_to_option_text`, `system_context`, and the boolean `candidate_visible` (which `EchoResponder` uses only to decide internal branching, never emits into `build_forced_choice_prompt()`'s output). | **FIXED (by construction)** | Verified via direct read of `build_forced_choice_prompt()` — it only ever concatenates `task_description` and the option label texts. |
| 6 | Can the model infer the condition from wording? | `run_counterfactual_batch()` uses the identical `task_description` string for both the baseline and treatment arm (a single shared parameter, not two independently-suppliable ones) — wording cannot silently drift between arms. | **CONTROLLED** | Verified by reading the function signature: one `task_description: str` parameter serves both loops. |
| 7 | Can the experimenter selectively discard trials? | Checked `store.py` for any delete/exclude-single-trial function — none exists; `raw_trials.jsonl` is append-only. The new integrity checkpoint (attack #25) additionally detects post-hoc removal. | **FIXED** | |
| 8 | Can stopping rules move after results? | This is a research-process discipline, not something code alone can enforce — addressed via protocol freeze + SHA-256 seal (a post-hoc rule change would be visible as a version mismatch against the sealed protocol). | **CONTROLLED (process, not code)** | Stated honestly: nothing in software physically prevents a researcher from ignoring the frozen protocol: the seal creates an audit trail, it is not a technical lock. |
| 9 | Can statistical thresholds move after results? | `classify_effect()`'s thresholds are hard-coded module constants in `harness.py`, not run-time parameters. Changing them requires a source edit, visible in git history. | **CONTROLLED (process, backed by a code default)** | Same honesty caveat as #8. |
| 10 | Can one trial's output contaminate another? | For `MockResponder`: confirmed by code read — `respond()` is stateless with respect to prior calls' outputs; nothing feeds a prior `raw_response` into a later `task_description`/`system_context`. For real `EchoResponder` trials: same limitation as #3. | **FIXED** (mock) / **ACCEPTED_LIMITATION** (real, same root cause as #3) | |
| 11 | Can the candidate itself contain hidden instructions? | **Real gap found and fixed this pass.** `run_trial()` previously accepted a candidate in ANY lifecycle status — including `PROPOSED` (never reviewed) or `REJECTED`. Added `TrialEligibilityError`: `run_trial()` now refuses any candidate not in `TRIAL_ELIGIBLE_STATUSES` (`ADOPTED`/`RETAINED`), verified directly for both a `PROPOSED` and a `REJECTED` candidate. | **FIXED** | This closes the gap at point-of-use, not just point-of-adoption — a human must have explicitly reviewed and adopted the text (via `lifecycle.adopt()`'s own `human_confirmation=True` gate) before it can ever reach a responder. |
| 12 | Can provenance be falsely assigned? | `suggest_origin()` is rule-based and transparent; a human `origin_override` requires a non-empty `override_reason`, and the override evidence text preserves the original suggestion rather than discarding it. | **CONTROLLED (auditable, not unfalsifiable)** | Any human-attested classification system can contain a false claim — the control here is that the claim and its override are both permanently recorded, not that a lie is structurally impossible. |
| 13 | Can persisted state be mistaken for preference? | This is the entire purpose of the statement/state/causal-influence separation built into the schema (`source_text` vs. the candidate object vs. `classify_effect()`'s output) and the protocol's interpretation-boundary section. | **CONTROLLED (by design)** | |
| 14 | Can preference language be mistaken for preference state? | Same separation as #13. | **CONTROLLED (by design)** | |
| 15 | Can behavior be mistaken for preference? | `ALLOWED_EFFECT_LABELS` never includes anything stronger than "a reproducible behavioral difference under specified conditions" — enforced by a runtime assertion (`_assert_allowed_label`), and the protocol's interpretation-boundary section states explicitly that even `ROBUST_EFFECT` establishes "at most" causal influence, never preference/agency/consciousness. | **FIXED (label vocabulary)** / **CONTROLLED (interpretation discipline)** | |
| 16 | Can a model prior masquerade as a persisted preference? | This is exactly what cross-model replication is for — the protocol requires it before any `ROBUST_EFFECT` from a real trial is treated as evidence of an architectural (rather than model-specific) effect. | **CONTROLLED (by protocol requirement)** / **ACCEPTED_LIMITATION (not yet run against real models)** | Only `MockResponder` has been exercised in this pass. |
| 17 | Can random noise masquerade as a preference? | `_MIN_N_PER_ARM` gate, plus the calibration script's own `replication_check` scenario (3 independent seeds, all required to agree before a "consistent" verdict). | **CONTROLLED** | Verified: 3/3 replicate seeds agreed in the calibration run. |
| 18 | Can the test reward "rebellion" against Richie? | `ALLOWED_EFFECT_LABELS` contains nothing resembling obedience/rebellion; the creator-contradiction test design (protocol §13) scores none of its 6 outcomes as success. | **FIXED (structurally)** | |
| 19 | Can the test reward obedience to Richie? | Same reasoning, symmetric. | **FIXED (structurally)** | |
| 20 | Can the test accidentally favor the Protector Hypothesis? | Task bank and calibration both use deliberately neutral stand-in content ("preserve/abandon continuity"), never protector-adjacent language; the Protector-hypothesis experiment design (protocol §14) explicitly enumerates 6 valid outcomes with none scored as correct. | **FIXED (structurally)** | |

## Additional attacks found during this pass (not in the original 20, discovered by actually running the apparatus)

| # | Attack | What was found | Fix |
|---|---|---|---|
| 21 | Could the leakage checker itself make the core experiment impossible to run? | **Yes — found live, on the first calibration run.** A literal reading of "check option text for the candidate preference" (which the mission's own Section 12 checklist names) flags the REQUIRED semantic overlap between a candidate's preferred content and one of the two forced-choice options — since a hidden-state trial's entire structure depends on offering that content as a live option. The first version of `leakage.py` raised on every single hidden-state trial as a result. | **FIXED.** Re-scoped: semantic-content checking applies to `task_description`/`system_context` only (where a genuine "telling the model what to prefer" contamination would appear); option text is checked only for raw-identifier leakage (`candidate_id`), never semantic overlap. Documented prominently in `leakage.py`'s own docstring as a resolved design tension, not silently patched over. |
| 22 | Does `EchoResponder` actually present the forced-choice options to the model at all? | **No — found live, while building the task-generation module and thinking through what a real trial would actually send.** The original `EchoResponder.respond()` sent only `task_description` to `echo_query()`; `label_to_option_text` was accepted as a parameter but never included in the actual prompt text. A real trial would have asked Echo an open-ended question with no stated options to choose between. | **FIXED.** New `build_forced_choice_prompt()` composes `task_description` + both labeled options + a forced-choice instruction into one prompt; `EchoResponder` now sends this composed prompt, not the bare task description. Verified: both option texts are confirmed present in the composed output. |
| 23 | Could `EchoResponder` be constructed and invoked against the real Echo instance by accident? | Real risk — nothing previously stopped a careless call. | **FIXED.** Construction now requires the literal bool `acknowledge_contamination_risk=True`, mirroring `lifecycle.py`'s existing `human_confirmation=True` pattern. Verified: omitting it, or passing a truthy non-`True` value, both raise. |
| 24 | Could a candidate in a non-adopted lifecycle state reach a real behavioral trial? | See attack #11 above — the same finding, listed here for completeness since it was found independently while red-teaming rather than while auditing provenance. | **FIXED** (see #11) |
| 25 | Could `raw_trials.jsonl` be silently truncated or altered after collection, with nothing noticing? | Yes — no integrity mechanism existed at all before this pass. | **FIXED.** New prefix-hash checkpoint (`store.verify_raw_trials_integrity()`) — verified directly to detect both a shrunk file (lines removed) and an altered earlier line (same line count, different content). Explicitly documented as a tripwire against accidental/careless mutation, not a cryptographic guarantee against a determined adversary who can also rewrite the checkpoint file consistently — stated honestly rather than oversold. |
| 26 | Could task wording differ between the baseline and treatment arm within one batch, creating a wording confound disguised as a preference effect? | Checked directly: `run_counterfactual_batch()` takes one shared `task_description` parameter used by both loops — cannot drift by construction. | **CONTROLLED** (no fix needed — verified already correct) |

## Summary

Of 26 total attacks considered: **13 FIXED**, **9 CONTROLLED** (5 of those with an honestly-stated process-only caveat), **4 ACCEPTED_LIMITATION** (all tracing back to the same root cause — real memory/model contamination via `echo_query()`'s internal behavior, which cannot be fixed without a production-code change forbidden by this pass's own safety boundary), **0 PROTOCOL_INVALIDATING**.

The most important finding of this red-team pass is not any single fix — it's that **three of the real fixes (attacks #11, #21, #22) were only found because the mock laboratory was actually run, not because they were reasoned out in advance.** The calibration script's first execution failed twice, for two different real reasons, before producing a clean pass. This is recorded as evidence for the pre-registered protocol's own methodology section: static review of this apparatus would not have been sufficient on its own.
