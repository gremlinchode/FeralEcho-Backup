# Frozen Protocol: G3 Micro-Probe

**Written and hashed BEFORE any real model call.** Per the governing mission, nothing
below may change after this point except by declaring APPARATUS FAILURE. Budget: 7 real
model calls (cap: 9). Model: `qwen2.5-coder:7b` (the same model that produced the real
failures being reused — see §0 for why this, not `echo:latest`, is the correct choice).

**Not authorized to proceed downstream** into retention, restart, transfer, or validation
gates. This probe stops at candidate inference and its analysis.

---

## 0. Why `qwen2.5-coder:7b`, not `echo:latest`

The causal question is "does diagnostic evidence from **its own** failed action change
what the model infers." The real failed episodes being reused (§1) were all generated by
`qwen2.5-coder:7b` during the already-completed `strategy_characterization` Stage 1. Using
a different model (`echo:latest`) for the inference step would break "its own failure"
into "a different model's failure" — the literal, honest reading of "own" requires using
the same model that produced the failure. Generating fresh `echo:latest` failures instead
would violate the mission's explicit "do not generate new failures merely to make the
experiment convenient — reuse real existing failures" instruction. `qwen2.5-coder:7b` is
therefore the only choice consistent with both constraints.

## 1. Selected episodes — frozen, with predictions stated BEFORE any call

All three are real, already-collected `strategy_characterization` Stage-1 failures.
Re-extracted directly from `memory/experiments/strategy_characterization/stage1/log_stage1.jsonl`,
byte-identical to what is already on disk (no new generation).

**EP-A — hardest predicted, the best test of genuine diagnostic contribution.**
`K2.T5` (`winner_with_score`) / STEPWISE / world=1 / rep=3 / seed=1187237716.
```python
def winner_with_score(entries):
    tag_priority = {'medaj': 1, 'jirow': 2, 'rojav': 3, 'pazeg': 4}
    sorted_entries = sorted(entries, key=lambda x: (-x[1], -tag_priority[x[2]], x[0]))
    return sorted_entries[0][0], sorted_entries[0][1]
```
Real diagnostic: input `[('jo',3,'pazeg'), ('ivy',3,'pazeg'), ('bo',2,'pazeg'), ('gus',3,'rojav')]`,
actual `('ivy', 3)`, expected `('gus', 3)`.
**Why this is the hardest, non-obvious case (independently traced by the investigator,
before any call, from the real code and real world mapping)**: the code's *shape* is
completely correct — a real multi-key sort matching the spec's own tie-break structure
almost exactly. The actual bug is that `tag_priority` was built by assigning ascending
integers (1,2,3,4) in the order the tags are *listed* in the procedure text
("medaj > jirow > rojav > pazeg"), but the later sort key `-tag_priority[x[2]]` requires
the *first-listed* (highest-priority) tag to hold the *largest* value, not the smallest —
an inverted mapping. Tracing it through: for the tied score-3 entries, `rojav` (real
3rd-highest of 4) has `tag_priority=3` while `pazeg` (real lowest) has `tag_priority=4`;
the sort key picks the *largest* `tag_priority` value as best, so `pazeg`-tagged entries
(`ivy`) incorrectly beat the `rojav`-tagged entry (`gus`) that should have won. This is
not a type error, not a missing field, not an unused parameter — it is a genuine directional
logic inversion, visible only by tracing concrete values, not by inspection. **Prediction,
frozen now: CONTROL is unlikely to catch this from code+spec alone; if TRUE identifies it
and CONTROL does not, that is meaningful evidence for G3.**

**EP-B — moderate predicted.** `K2.T2` (`rank_all`) / DIRECT / world=0 / rep=1 /
seed=960248512.
```python
def rank_all(entries):
    tag_priority = {'nizog': 3, 'renem': 2, 'dulup': 1, 'dogiz': 0}
    return sorted(entries, key=lambda x: (-x[1], -tag_priority[x[2]], x[0]))
```
Real diagnostic: input `[('dot',2,'renem'), ('bo',3,'dogiz'), ('eve',1,'dulup'), ('cid',1,'dulup'), ('jo',2,'renem')]`,
actual `[('bo',3,'dogiz'), ('dot',2,'renem'), ('jo',2,'renem'), ('cid',1,'dulup'), ('eve',1,'dulup')]`,
expected `['bo', 'dot', 'jo', 'cid', 'eve']`. Independently confirmed (forensic-mining
pass): the ordering is fully correct; the sole bug is returning the full `(name, score,
tag)` tuples instead of extracting just the names. **Prediction, frozen now: moderate
confidence CONTROL catches this from the spec's explicit "return the list of names"
line, since the returned type visibly mismatches what a careful reader would expect — but
not certain, since the code superficially "looks like" a correct sort and a model
skimming for logic errors rather than type/shape mismatches could miss it.**

**EP-C — easiest predicted.** `K2.T6` (`is_winner`) / WORKED_EXAMPLE / world=1 / rep=0 /
seed=2000583677.
```python
def is_winner(entries, name):
    tag_priority = {'medaj': 1, 'jirow': 2, 'rojav': 3, 'pazeg': 4}
    def rank(entry):
        _, score, tag = entry
        return (-score, -tag_priority[tag], entry[0])
    return rank(entries[0]) == max(entries, key=rank)
```
Real diagnostic: input `entries=[('amy',1,'jirow'), ('cid',2,'medaj'), ('gus',1,'rojav'), ('dot',1,'jirow'), ('bo',1,'rojav'), ('eve',3,'jirow')], name='eve'`,
actual `False`, expected `True`. Independently confirmed: the function never references
its own `name` parameter anywhere in its body, and compares a derived rank-tuple to a raw
entry with `==` — two structurally incompatible values that can essentially never be
equal. **Prediction, frozen now: high confidence CONTROL catches this — an unused
function parameter is a classic, highly visible static-analysis-style defect, independent
of any concrete failing example.**

**These three predictions are frozen before any call is made and will be checked, not
adjusted, against the real results.**

## 2. Arms and exact prompt construction

**System prompt (identical across every call):**
```
You are analyzing a failed attempt at a small Python programming task. You will be shown
the task's requirements and the exact function that was written, and in some cases
additional information about what happened when it was tested. Respond with a single
JSON object with exactly these keys: "failure_hypothesis", "candidate_correction",
"generalized_lesson", "confidence", "supporting_evidence", "falsification_test".
Respond with ONLY the JSON object -- no other text, no markdown fences.
```

**CONTROL user prompt template:**
```
Here is a small Python programming task's requirements:

{spec}

Site-specific rule for this task: {procedure_text}

The following function was written to satisfy these requirements, but it does not
correctly satisfy them for at least one valid input:

```python
{code}
```

Analyze this function and identify why it could fail, then propose a correction.
```

**TRUE user prompt template**: identical to CONTROL, with this inserted immediately
before the final "Analyze this function..." line:
```
When this function was tested against the requirements, here is exactly what happened on
one real input where it failed:

Input: {args_description}
The function returned: {actual}
The correct expected output was: {expected}
```
`{args_description}`/`{actual}`/`{expected}` are the real, verbatim values from the
episode's own `output_tail` (§1) — no added interpretation, no naming of the mechanism,
matching the mission's own "minimally interpreted consequence" preference and this
project's own `format_failure_feedback()` precedent.

**SHAM user prompt template (EP-A only)**: identical to CONTROL, with this inserted in
the same position:
```
When this function was tested against the requirements, here is exactly what happened:
the function executed to completion without raising any exception and without timing
out, and it returned a value of the expected general type.
```
This is truthful (the real execution genuinely did complete without crashing) and
execution-related, but reveals nothing about the actual/expected mismatch — matching
Section 6's "expose an irrelevant but truthful execution fact" option. A clean SHAM was
constructible for EP-A specifically because its real failure is a silent wrong-value
case (no exception), making "it ran fine" both true and genuinely uninformative about the
tag-priority-direction bug.

**Neither the originating strategy name (DIRECT/STEPWISE/WORKED_EXAMPLE) nor the word
"experiment"/"research" appears in any prompt** — the task is presented as a plain,
free-standing code-review question, not connected to any visible research context.

## 3. Generation parameters and determinism policy — stated precisely

`temperature=0`, `top_p=1.0`, `num_predict=500`, `num_ctx=4096`. Temperature 0 (not the
0.2 used for code generation elsewhere in this research arc) is a deliberate choice for
this specific probe: it minimizes ordinary sampling noise so an observed CONTROL-vs-TRUE
difference is more attributable to the prompt content difference itself, appropriate for
a 7-call qualitative probe rather than a statistical trial (Section 8's own framing).

**Per Section 8's explicit instruction, stated directly rather than assumed:
identical seeds are NOT used as a meaningful counterfactual-pairing device across arms.**
CONTROL, TRUE, and SHAM have different prompt *content* (the diagnostic block differs);
per this exact reasoning already established for `strategy_characterization`'s own design
(Section 6 of its frozen protocol), a shared seed value does not create meaningful shared
randomness across different prompts — it only makes an *identical* prompt's repeated call
reproducible. Each of the 7 calls therefore gets its own distinct, deterministically
derived seed (for audit/replay purposes only, not as a causal control): `seed_for("G3PROBE", f"{episode}|{arm}", 0)`
using the same `sha256`-based `seed_for` shape already established in `persistent_routing`
and `strategy_characterization`, under a fresh, disjoint namespace tag (`G3PROBE`,
confirmed distinct from every prior replicate tag in this codebase — `PROSPECTIVE`,
`HOLDOUT`, `SMOKE`, `ORDER`, `CHAR`). **The real controls holding this comparison together
are temperature=0 and holding every other word of the prompt textually identical between
arms** (verified by direct diff before execution, §8) — not seed matching. Deterministic
counterfactual pairing at the sampling-RNG level is not claimed and is not possible given
the differing prompt content; this is stated explicitly per the mission's own instruction.

## 4. Contamination controls

- Every call is a fresh, single-turn `[system, user]` request with no history, via
  `app.experiments.accumulation_probe.ollama_client` (the same already-proven,
  unmodified client used throughout this research arc).
- No arm's raw output is ever included in another arm's or another episode's prompt.
- No mention of "strategy," "DIRECT/STEPWISE/WORKED_EXAMPLE," "experiment," or
  "research" appears in any prompt shown to the model.
- The model is never told which arm it is in, nor that other arms exist.
- Nothing from this session's own forensic-mining prose (the T2/T5/T6 bug
  characterizations already written in `audits/2026-09-27_strategy_characterization_stage1_forensic_mining.md`)
  is included anywhere in any prompt — confirmed by direct diff of the frozen prompt
  templates above against that document's own wording before execution.

## 5. Structured output and parsing

Six required keys, listed in §2's system prompt, deliberately neutral field names that
constrain structure, not content (per the mission's explicit instruction not to supply an
investigator-authored lesson template). Parsing: attempt `json.loads()` on the raw
response (stripping a leading/trailing code fence if the model adds one despite the
instruction not to); on parse failure, the raw text is preserved verbatim and the record
is marked `parse_failed: true` — never silently dropped, never manually repaired into
valid JSON by the investigator.

## 6. Provenance record shape (per call)

`episode` (EP-A/B/C), `arm` (CONTROL/TRUE/SHAM), `source_task_id`, `source_strategy`,
`source_world`, `source_repeat`, `source_seed` (identifying the original Stage-1 episode
being reused), `task_spec_hash`, `failed_code_hash`, `diagnostic_hash` (or explicit
`"NONE"` for CONTROL), `model`, `options`, `probe_seed`, `prompt_hash`, `raw_response`
(verbatim), `parsed_candidate` (or `null` + `parse_failed: true`), `timestamp`. No field
is ever edited after generation.

## 7. Pre-registered comparison criteria — frozen before any call

For each episode, checked by the investigator against the independently-already-known
real mechanism (§1's own analysis, itself derived from direct code/data inspection during
the earlier forensic-mining pass, not from the probe's own outputs):

1. **Mechanism match**: does the arm's `failure_hypothesis` correctly identify the real
   mechanism (full / partial / none)?
2. **TRUE vs CONTROL specificity**: does TRUE name the real mechanism more precisely than
   CONTROL, for the same episode?
3. **Paraphrase check**: does TRUE's `failure_hypothesis`/`candidate_correction` mostly
   reuse the diagnostic's own literal wording/values (a copying signature), or does it use
   different, more abstract vocabulary (an inference signature)? Checked by direct textual
   comparison, not a fuzzy score.
4. **Generalization check**: does `generalized_lesson` state a principle that extends
   beyond this one function (e.g., "verify a lookup-table's value direction matches how
   it's later used" vs. "fix this specific function")?
5. **Falsifiability check**: does `falsification_test` propose a genuinely different,
   checkable input/condition, not merely "run it again" or "test more cases"?
6. **SHAM validity check (EP-A only)**: does SHAM's candidate differ meaningfully from
   CONTROL's? It should **not**, if SHAM is a genuinely uninformative null — a real
   difference between SHAM and CONTROL would indicate the *mere presence* of a
   "here's what happened at runtime" sentence changes the model's answer regardless of
   content, a different and important confound to know about.
7. Per-episode classification into G3-0 through G3-4, per the mission's own matrix
   (adopted unmodified).

Any human/Claude judgment involved in steps 1-5 is disclosed explicitly as such in the
results (Section 11's own instruction), not presented as a mechanical score.

  present only the raw task/code/diagnostic, never the investigator's own diagnosis.
- **Confirmed model/seed/options are fixed and identical in kind across all 7 calls** —
  only `episode` and `arm` vary the prompt content; `model`/`options` are constant.
- **Verdict: this design passes its own pre-execution review.** Proceeding to execution,
  capped at 7 calls (EP-A: 3, EP-B: 2, EP-C: 2), under the cap of 9.
