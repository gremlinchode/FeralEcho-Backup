## 1. Defining the target

FeralEcho already has real, working versions of the first several rungs of the ladder — the operative question is not "does storage/retrieval exist" (it does, extensively) but which of the *harder* rungs is worth spending real research effort on next, given the resources actually available.

- **Storage** — extensively real. 128,837 real memory entries at last count (RETRIEVED, this session's archaeology's own citation of the zero-cost-ceiling report), 207,554 real RiverBrain observations (OBSERVED, this session's own reward-wire audit).
- **Retrieval** — real and working (FAISS + sentence-transformers), but its downstream *consumption* is the one place this project has already run a real, controlled ablation and found a **null result**: RETRIEVED, CLAUDE.md's Finding 76, a real 30-prompt (plus 5-pair noise-floor calibration) memory-ablation experiment found the control-vs-ablation embedding-distance distribution statistically indistinguishable from ordinary sampling noise. This is a genuinely important, already-paid-for negative result this report treats as load-bearing throughout, not merely cited in passing.
- **Within-context adaptation** — trivially real of any LLM; not a FeralEcho-specific achievement, and not worth further research investment on its own.
- **Persistent state** — real, but heterogeneous in reliability: RiverBrain's pickle survives restart but carries a live, confirmed background-writer-thread contamination risk (OBSERVED, this session's reward-wire audit, §16 of that report); `behavioral_state.py`'s JSON store is the single most cleanly restart-proven artifact in the whole codebase (RETRIEVED, this session's own sibling audit); `self_model_claims.jsonl` persists reliably but is 17.4% write-only-orphaned by a real bug (OBSERVED, this session's own sibling audit).
- **Behavioral adaptation** — real but narrow: confirmed for RiverBrain's routing decision (a direct, deterministic sort-key dependency, OBSERVED, this session's reward-wire audit §8) and for `behavioral_state.py`'s directive injection (real, but gated to near-unreachability for ordinary human conversation, OBSERVED, this session's sibling audit).
- **Routing/policy learning** — the one rung with a real, if heavily contaminated and Simpson's-paradox-confounded, existing claim (RETRIEVED, this session's archaeology's Tier-7 citation: RiverBrain correctly detects one specific unreliable model, worse than chance on the pairing that matters most).
- **Acquired competence, transfer, structural/generalized transfer, repeated accumulation, accumulated competence** — **none of these have ever been demonstrated in FeralEcho's real production history, for any mechanism, at any scale.** Every design targeting them (the frozen persistent-competence protocol v1.1, E5-mini) exists only as an adversarially-hardened, never-executed specification (RETRIEVED, this session's archaeology).

**What this report recommends pursuing next, stated plainly before the rest of the analysis:** FeralEcho should pursue **routing/policy learning** (cheap, mostly-designed, real if modest value) **and, in parallel, a first genuine, cheap attempt at held-out transfer through a validated procedure/skill library** — not through RiverBrain, not through fine-tuning, but through curated, F2-verified context. The reasoning for both choices, and why acquired competence in the "a model gets smarter" sense is ruled out entirely under the zero-cost constraint, is developed in full below (§7 answers Questions A and B separately, as instructed).

## 2. The system as a whole — where experience enters, what's discarded, what's retained

**Where does useful experience currently enter the system?** Four real, high-volume entry points, cross-checked this mission against the reward-wire audit's own direct source read: (1) every real model response, across every task type — feeds `RiverBrain.learn()`; (2) real F2 sandbox executions, both from self-edit's own generation pipeline and from conversational code-verification — 16,208 real observations for `coding` alone (OBSERVED, this session's reward-wire audit); (3) real human 1-5 ratings and real peer-council ratings; (4) real autonomous activity — reflection cycles, curiosity-garden question generation, `echo_projects.py`'s own autonomous spec-generation-and-build cycle (OBSERVED this report, §3: `autonomous_generate_project()` genuinely calls `garden_manager.select_from_garden()` and builds a real, multi-file, F2-verified project from whatever question the garden surfaces).

**Which experiences have trustworthy outcome signals?** Only one class, cleanly: real, deterministic sandbox execution (F2) — the single most independent, highest-volume signal this project has, per the reward-wire audit's own direct §9 attack. Human ratings are real but sparse and preference-conflated, not correctness-verified. Peer-council ratings are real but still an LLM's opinion, not ground truth. Every other "experience" (an ordinary conversational response, an autonomous reflection) has no outcome signal at all beyond a response scoring its own text.

**What information from those experiences is currently discarded?** The single largest, most concrete, already-quantified answer this project has: **16,208 real, independent sandbox verdicts, computed and then discarded at an exact, named method boundary** (OBSERVED, this session's reward-wire audit) — never reaching the one statistic (`model_task_stats`) that actually influences behavior. This is not a hypothetical waste; it is a real, already-computed signal sitting unused today.

**What is retained?** A great deal, but almost entirely as either (a) a self-referential rolling statistic (RiverBrain's dominant `learn()` path, 207,554 observations, none independently verified) or (b) raw, undifferentiated text (128,837 memory entries with, per the zero-cost-ceiling report's own explicit finding, RETRIEVED, "no explicit epistemic types" distinguishing a validated fact from autonomous rambling from a human correction).

**What retained state actually changes future behavior?** Three real, confirmed paths, and only three: RiverBrain's `score_model()` → `rank_models()`/`choose_model()` (unconditional, real, OBSERVED); `behavioral_state.py`'s directive injection (real but gated to near-unreachability, OBSERVED); `self_model_claims.py`'s corrective-note injection (real but confined to prompt text and, per this session's own sibling audit, indistinguishable from a fixed counterfeit on the evidence available). **Everything else this project has built — the curiosity garden, the seam engine, the dream cycle, the salience/valence machinery — either has no behavioral consequence beyond its own logging, or has one only within its own narrow autonomous-loop context, never in a way any of this session's four prior audits found reaching a genuinely held-out test.**

**Which mechanisms adapt but lack trustworthy evaluation?** RiverBrain's dominant `learn()` path (self-scored), `self_model_claims.py` (independently evaluated, but only within a hardcoded 5-subject vocabulary), the task-type classifier (RETRIEVED, this session's archaeology's own citation of the persistent-competence candidate tournament: its own training label is generated by the same keyword-heatmap ladder it exists to supplement — a soft circularity).

**Which mechanisms have trustworthy evaluation but lack behavioral consequence?** This is the single most important structural finding this report can state plainly, because it is the exact inverse of the previous question and names the real bottleneck: **real F2 sandbox execution outcomes** (trustworthy, high-volume, currently discarded before reaching any consumer) and, more speculatively but plausibly, **`echo_projects.py`'s own F2-verified build outcomes** (a real, independent pass/fail per autonomous project, currently used only to decide whether to write a status report — RETRIEVED from CLAUDE.md's own extensive documentation of this pipeline, not independently re-verified beyond this report's own §3 spot-check of its real wiring).

**Where are the bottlenecks?** Precisely two, and this report treats them as the two load-bearing findings underneath everything else: (1) the reward-wire disconnection (§ above, already fully designed-against in this session's own prior audit); (2) the **consumption problem** — even when independently-relevant information genuinely reaches a model's context (Finding 76's own retrieval-ablation trial confirmed this happens), there is no confirmed evidence that generation reliably *uses* it in a way that improves outcomes, as opposed to merely being present.

**What machinery exists but is dormant?** `river.bandit` (RETRIEVED, reconfirmed zero real call sites this session, twice independently); `behavioral_directives.json`'s own store (currently zero real directives, RETRIEVED); the seam engine's own real detections (83 in the historical corpus per CLAUDE.md, with zero measured downstream effect ever checked, RETRIEVED); `project_learner.py`'s AST/import-summary exports (RETRIEVED, the zero-cost-ceiling report's own characterization, "makes information potentially available," never confirmed consumed by anything).

**What research has already solved part of the problem but was abandoned or disconnected?** The frozen persistent-competence protocol v1.1's own already-adversarially-hardened counterfeit-learner defenses (the HMAC tie-break, the null-effect/positive-control battery, the structural-novelty held-out design) — fully specified, never run, and, per this session's own archaeology, apparently unconnected to the research effort that actually shipped (Rung-1/`accumulation_probe`). E5-mini's own repeated qualification cycle — a real, hard-won finding that its own accounting-layer apparatus had a *structural*, not-patchable detection gap — is itself valuable negative-methodological knowledge that this report reuses directly (§5's chosen falsification test).

**What mechanisms appear promising but are actually scientific dead ends, on the evidence this project already has?** Two, named plainly: (1) **raw semantic-similarity memory retrieval as a behavior-change mechanism** — Finding 76's own null result is real, controlled evidence, not a hunch, and this report does not recommend investing further in "retrieve more relevant text" as a strategy on its own. (2) **crediting the synthesized final answer as the object of learning** — RETRIEVED, this project's own well-documented Tier-4/5 research finding (this session's archaeology, §7 of that report) that council synthesis measurably *loses* information relative to the best raw candidate; `RiverBrain.learn(ECHO_SYNTHESIS_MODEL, ...)`'s own existing practice of training on the synthesized text is, on this project's own evidence, training on a demonstrably lossier signal than what was actually available pre-synthesis.

## 5. Attacking every proposal before making one

Per the mission's own instruction, every approach below is pre-attacked with the same question: *what simpler, non-learning mechanism could produce the same apparent improvement?* Three approaches are developed in full (§6); a fourth, meta-level option ("stop building mechanisms, fix evaluation project-wide") is folded into the comparison rather than developed as a fifth mechanism, since it is a research-priority stance, not itself a learning mechanism.

**The single cheapest, highest-information falsification test this report can propose, independent of which approach is ultimately chosen:** re-run the *scientific question* E5-mini was built to answer (does a taught, validated procedure transfer to a structurally held-out task?) using F2's already-existing, dead-simple pass/fail sandbox as the *sole* evaluator, deliberately **not** rebuilding E5-mini's own more elaborate accounting-layer apparatus, which is precisely the component that failed its own qualification cycle three separate times (RETRIEVED, this session's archaeology's own citation of the E5-mini lineage). E5-mini's own repeated failures were about its *instrumentation*, not about the underlying hypothesis being wrong — this report's own reading of that lineage (§2) is that the scientific question itself was never actually tested, only the apparatus meant to test it. A minimal P (taught, validated procedure) vs. Z (zero-teaching, same construction budget) comparison, on a small, cheap, F2-checkable task family, with F2's own pass/fail as the entire oracle, is buildable from components this project already has and already trusts, without inheriting E5-mini's own more complex, previously-failing accounting layer.

## 6. Three materially different approaches

### Approach 1 — Fix the routing-learning reward wire (reuse this session's own prior design)

- **Mechanism:** connect the real, currently-discarded F2 sandbox-outcome signal to a *fresh, isolated* statistic (not live `model_task_stats`), consumed by a `score_model()`-shaped function, per this session's own reward-wire audit's §17 design.
- **What changes through experience:** which of the already-installed, fixed models gets selected for a given task type.
- **Evaluator:** real F2 sandbox pass/fail — already the most independent, highest-volume signal this project has (16,208 real observations for `coding` alone).
- **Retained representation:** a per-`(model, task_type)` cumulative mean, structurally identical to the frozen protocol's own already-specified carrier shape.
- **Behavioral consumer:** a routing decision — real, unconditionally reachable, deterministic.
- **Restart behavior:** clean, following `behavioral_state.py`'s own already-proven no-cache, atomic-write persistence pattern.
- **Expected transfer:** none claimed beyond routing — this approach never touches the underlying models.
- **Computational cost:** effectively zero marginal cost — the signal already exists; only a new, small persistence layer is required.
- **Implementation complexity:** low-moderate; mostly already designed (this session's own §17/§18).
- **Major failure mode:** the fixed-policy/identity-effect counterfeit (a routing rule that just keeps favoring the already-dominant model, per this session's reward-wire audit's own §15 attack) — real and concretely demonstrated to be a live risk given `echo:latest`'s current 63,071-observation dominance.
- **Falsification test:** the frozen protocol's own null-effect calibration with a hand-typed carrier (RETRIEVED, `[QUAL-4]`(d)) — if a fixed, hand-typed "always prefer the historically-dominant model" carrier passes the same statistical bar as a genuinely learned one, the approach has failed to distinguish itself from its own strongest counterfeit.
- **Strongest legitimate claim if successful:** genuine, held-out, restart-surviving routing/policy learning among fixed models — real and valuable, but explicitly **not** capability acquisition (per this session's own reward-wire audit §14's architectural argument, which this report does not re-litigate and fully accepts).

### Approach 2 — A validated, F2-verified procedure/skill library (this report's own preferred approach, developed fresh)

- **Mechanism:** whenever a real F2-verified sandbox execution succeeds on a genuinely novel task (not a retry of the same task), store the validated `(task family signature, worked solution)` pair in a small, bounded, deterministically-keyed store — architecturally modeled on `behavioral_state.py`'s own proven persistence shape (atomic write, no cache, no singleton, restart-proof, RETRIEVED), **not** on RiverBrain's rolling-mean shape, and **not** on raw FAISS semantic retrieval. Retrieval is by exact or near-exact task-family signature match (e.g., the same deterministic AST-approach-bucket classification the RAOC/frozen-protocol lineage already built and validated, RETRIEVED from this session's archaeology), never by embedding similarity — a deliberate design choice to avoid inheriting Finding 76's own already-demonstrated null result for similarity-based retrieval.
- **What changes through experience:** the *content available in context* for a future task recognized as belonging to an already-solved family — not which model is chosen, and not any model's own weights.
- **Evaluator:** the same real F2 sandbox pass/fail used in Approach 1 — reused, not reinvented, and, critically, applied to **pre-synthesis raw candidate code**, not the synthesized final answer, per §2's own dead-end finding about synthesis being measurably lossier.
- **Retained representation:** a small, bounded, provenance-tagged JSON store — task-family signature, validated code, the model that produced it, the timestamp, and an explicit `requalification_due` field (§9's forward-looking need).
- **Behavioral consumer:** a context-injection function, structurally identical in shape to `_build_behavioral()` (RETRIEVED, this session's sibling audit) — but, critically, **wired to fire unconditionally whenever a task-family signature match is detected**, not gated behind `_is_introspective()` or any topic-relevance heuristic, closing exactly the reachability gap this session's own `behavioral_state.py` audit found (§7 of that report).
- **Restart behavior:** clean, by construction, following the same proven pattern.
- **Expected transfer:** the entire point of this approach — held-out transfer within the *same* task family (a new instance of a previously-solved pattern) is the primary claim; structurally novel transfer (a genuinely different pattern) is explicitly not claimed without further, separate evidence.
- **Computational cost:** zero marginal cost beyond what F2 already computes; retrieval is a cheap deterministic lookup, not an embedding search.
- **Implementation complexity:** moderate — smaller than Approach 1's own reward-wire isolation work in some respects (no shared-statistic contamination risk to design around, since each procedure is a standalone record), but requires a new, careful task-family-signature classifier (reusing, not reinventing, the RAOC lineage's own already-built and validated `approach_classifier.py`, RETRIEVED, this session's archaeology).
- **Major failure mode, attacked directly per the mission's own instruction:** the exact counterfeit already proven for `behavioral_state.py` in this session's own sibling audit — a fixed, hand-authored library of generic coding tips could produce an apparently-identical improvement with zero learning loop at all, **if** the stored "procedures" turn out to be generic style advice rather than genuinely task-specific worked solutions. The defense is that a genuine procedure here is, by construction, a *specific, validated solution to a specific, previously-encountered task family* — content a human could not plausibly have pre-authored without having already seen that exact family solved — but this defense must be checked empirically (the frozen protocol's own semantic-duplication and procedure-authoring-blindness controls, RETRIEVED, are directly reusable for this check) and is not assumed true by this report. **A second, more serious failure mode, named honestly rather than glossed over: this approach could fail for exactly the same reason Finding 76's raw-retrieval ablation already failed** — if generation simply does not reliably *consume* injected context regardless of its validation status, then validating the content more rigorously than raw memory retrieval does would produce no measurable improvement over that same null result, for a reason entirely outside this approach's own control (a foundation-model-level limitation, not an engineering gap this project can close at zero cost). This is this report's own single most important, honestly-stated risk (see §8, item 6).
- **Falsification test:** exactly §5's own proposed minimal experiment — a P (validated procedure) vs. Z (zero-teaching, matched construction budget) comparison on a small, F2-checkable held-out task set, using F2's own pass/fail as the sole oracle.
- **Strongest legitimate claim if successful:** genuine, held-out, same-family transfer through validated context — the first FeralEcho result, at any scale, to license a claim above Level 4 on this session's own reward-wire audit's claim ladder (§13 of that report), while still explicitly stopping short of structural/generalized transfer or accumulated competence without further evidence.

### Approach 3 — A self-generated curriculum, spaced-retest accumulation loop

- **Mechanism:** use the already-real, already-autonomous curiosity-garden/`echo_projects.py` pipeline (§2, §3) as the *task-generation* engine, rather than a fixed, human-authored task family list — whenever `garden_manager.select_from_garden()` surfaces a question `echo_projects.py` can translate into a buildable, F2-checkable spec, treat the resulting build as one real learning episode, and periodically (per the frozen protocol's own already-designed `[LONG-1]`–`[LONG-8]` spaced-retest shape, RETRIEVED) re-attempt a *fresh* variant of a previously-attempted family to test retention over real elapsed time, without re-teaching.
- **What changes through experience:** which task families accumulate a validated procedure (feeding directly into Approach 2's own store, if built), and — separately, more speculatively — whether Echo's own self-generated curiosity increasingly favors families where it has previously succeeded versus struggled (an exploration/exploitation question, currently entirely unaddressed anywhere in this codebase, §9).
- **Evaluator:** the same F2 oracle, reused.
- **Retained representation:** Approach 2's own store, plus a per-family attempt/outcome history for the spaced-retest design.
- **Behavioral consumer:** the same as Approach 2, plus the curiosity-garden's own existing selection-weighting mechanism (real, already-live, RETRIEVED).
- **Restart behavior:** clean, by construction (same pattern reused throughout).
- **Expected transfer:** this is explicitly the *repeated accumulation* rung, not merely single-episode transfer — the only approach of the three that directly targets Levels 7-8 on this session's reward-wire audit's ladder, at the cost of being the most speculative and the longest-horizon of the three.
- **Computational cost:** low, since it reuses `echo_projects.py`'s existing 6-hour autonomous cadence (RETRIEVED, CLAUDE.md's own documentation) rather than requiring new inference infrastructure.
- **Implementation complexity:** highest of the three — requires wiring Approach 2's store into an already-complex, multi-part autonomous pipeline, plus building the spaced-retest scheduling logic from scratch (the frozen protocol's own design exists only for a fixed, hand-authored task family, not a self-generated one).
- **Major failure mode:** self-generated curiosity questions may simply not translate into a sufficiently narrow, F2-checkable task family often enough to accumulate meaningful statistics — a real, plausible risk this report cannot rule out without running it, since `echo_projects.py`'s own real historical success rate (per CLAUDE.md's own Finding 91, RETRIEVED) shows the majority of its autonomous attempts fail F1/F2 for mundane reasons (leading prose, matplotlib sandbox friction) unrelated to the underlying task's genuine difficulty — meaning much of the "curriculum" this approach would generate may be noise from apparatus friction, not genuine task-difficulty signal, unless that friction is first cleaned up.
- **Falsification test:** track, over a fixed real-time window (e.g., two real weeks of the existing 6-hour cadence), what fraction of autonomously-generated specs ever reach a clean F2 pass at all — if this fraction stays near the historically low rate CLAUDE.md's own Finding 91 already documented before its own fixes, the self-generated-curriculum premise is not yet viable and needs its own apparatus-reliability work first, independent of anything this report proposes.
- **Strongest legitimate claim if successful:** a genuine, self-directed, repeated-accumulation result — the only one of the three approaches that could, in principle, ever reach Level 7-8 on the ladder, though also the one furthest from being buildable cheaply and quickly.

## 7. Making a choice — and answering A and B separately

**Question A — best path toward persistent routing/policy learning:** **Approach 1, exactly as this session's own prior reward-wire audit designed it (§17/§18 of that report).** Nothing in this fresh, first-principles pass changes that conclusion — it was already the minimum, best-defended design available, and re-deriving a different one here would not improve on it. The one refinement this report adds: prioritize it *second*, not first, in overall research sequencing (§7's closing choice), because Approach 2's falsification test is cheaper and answers a more consequential open question.

**Question B — best path toward actual acquired competence:** **Not Approach 1 — Approach 2.** And the honest, load-bearing architectural fact this report states plainly, per the mission's own explicit request: **the ceiling on acquired competence in FeralEcho, under the zero-cost constraint, is exactly the boundary between what lives in a fixed model's weights and what can be supplied through context.** RiverBrain, `river.bandit`, or any future routing mechanism can never cross this ceiling — routing only ever chooses among fixed capabilities, per this session's own reward-wire audit's §14 architectural argument, which this report independently re-affirms rather than merely repeats: there is no mechanism, anywhere in this codebase's design space, by which choosing a model more wisely could make that model itself more capable. **What CAN be accumulated, on FeralEcho's surrounding architecture, without touching a single model weight, is a growing, validated library of context that raises the *effective* performance of whichever fixed model receives it — genuine, if narrow, competence at the system level, achieved entirely through what is supplied around a frozen model, not through any change inside one.** This is not a consolation prize; it is the actual, correct target given the constraint, and Approach 2 is this report's own fresh answer for how to pursue it, distinct from every mechanism this session's four prior audits examined.

**The choice, if this report's author were responsible for FeralEcho's research direction: pursue Approach 2 first, using §5's minimal falsification test as the very next concrete action — before Approach 1, before Approach 3, and before any further RiverBrain-adjacent work of any kind.** Reasoning: Approach 2's falsification test is the cheapest of the three to run, it directly re-tests the single most consequential open question this project's own evidence already raises (does validated, task-specific context actually change behavior, where raw retrieval already failed to), and a clean negative result would be exactly as valuable as a positive one — it would definitively establish that FeralEcho's ceiling under the zero-cost constraint is lower than hoped, for a real, evidenced reason (a foundation-model consumption limitation), redirecting all future research effort away from context-based competence entirely and toward Approach 1's narrower, more modest, but achievable routing-learning goal instead.

- **One mechanism to stop spending research time on:** treating **synthesized text as the object of learning**, project-wide — not a specific module, but a practice (`RiverBrain.learn(ECHO_SYNTHESIS_MODEL, ...)`'s own current design, and any future mechanism that would credit "Echo's final answer" rather than the pre-synthesis candidates that produced it). This project's own Tier-4/5 research already demonstrated synthesis is measurably lossier than the best raw candidate (§2); continuing to build learning signals around the lossy output rather than the richer input underneath it is a real, avoidable, already-evidenced mistake.
- **One existing mechanism this report considers undervalued:** **`echo_projects.py`'s autonomous spec-generation-and-build pipeline.** Every prior audit this session produced treated it as a self-edit-adjacent curiosity, never as what it structurally is: the one already-built, already-running, already-F2-verified translator from open-ended self-generated curiosity into checkable, falsifiable artifacts — exactly the missing piece Approach 3 needs, sitting unused for this purpose today.
- **One missing capability this report considers most important:** a **deterministic, task-family-keyed retrieval mechanism, architecturally separate from FAISS's semantic-similarity memory** — the specific, concrete missing piece Approach 2 depends on, and the direct answer to why Finding 76's own null result does not, on its own, foreclose this report's recommendation (similarity-based retrieval and family-keyed retrieval are different mechanisms with different failure profiles, and only the former has actually been tested).
- **One experiment with the greatest information gain per unit of compute/time:** §5's minimal P-vs-Z, F2-oracle-only procedure-transfer test — cheaper than either Approach 1's or Approach 3's own first concrete step, and directly resolves the single most consequential open uncertainty this whole report turns on.
- **One architectural change with the greatest potential increase in genuine learning capacity:** a **shared, cross-mechanism evidence/provenance-quality layer** — replacing the three separate, bespoke, ad hoc provenance schemes this session's own audits found (RiverBrain's `council_vetted_count` counter, `self_model_claims.py`'s `KNOWN_SUBJECTS`/`proposed_by != verified_by` guard, `behavioral_state.py`'s `human_confirmed` gate) with one shared notion of "how trustworthy is this stored fact, and why" that any future mechanism — including Approach 2's own procedure library — could consume without re-inventing its own narrow provenance rule from scratch. This is a larger, more structural recommendation than any single mechanism above, offered because the mission explicitly asked for one.
- **One reason this preferred approach might still fail completely:** stated already, and repeated here because it is the single most important honest risk in this report — **the consumption problem may not be specific to raw retrieval at all.** If generation simply does not reliably act on injected context regardless of how well-validated that context is, Approach 2 fails for a reason entirely outside FeralEcho's own engineering control, and no amount of better provenance, better retrieval, or better validation closes that gap. This is exactly why §5's minimal experiment is proposed as the first, cheapest action rather than committing to building the full procedure-library infrastructure on faith.

## 8. Attacking the choice one more time, explicitly

Re-applying the mission's own full counterfeit checklist to Approach 2 specifically, beyond §6's own attack: **evaluator leakage** — mitigated by reusing F2 directly rather than a self-supplied "expected output" check (this session's reward-wire audit's own §9 finding that code-verification's current production path uses a self-supplied reference is a real, relevant caveat — Approach 2 should use F2's hidden-test-shaped variant, not code-verification's self-supplied one, where available). **Self-evaluation** — avoided by construction, since F2 never re-uses the candidate's own claims. **Selection effects** — real, and requires the same forced-exploration discipline the frozen protocol already specifies (RETRIEVED), applied to which task families get attempted at all. **Identity/order effects** — not directly applicable, since Approach 2 does not select among models, only among stored procedures. **Fixed policies masquerading as learning / retrieval masquerading as learning / prompt adaptation masquerading as persistence / persistence masquerading as competence** — all four are exactly the family of risks §6 and §8's own closing item already name as the approach's central, unresolved vulnerability. **Simpson's paradox** — a real, plausible risk if a small number of easy task families dominate the store and produce most of the apparent "transfer," masking a lack of genuine discrimination on harder families; this would need the same subgroup-analysis discipline this project's own Tier-7 forensic work (RETRIEVED) already demonstrated is necessary. **Task-distribution artifacts, stale state, write-only state, unreachable consumers, contaminated experiments, insufficient restart isolation** — each is directly addressed by, respectively: the frozen protocol's own held-out family design; a `requalification_due` field (§9); `behavioral_state.py`'s own proven no-orphan read pattern (unlike `self_model_claims.py`'s own confirmed 17.4%-orphan bug, deliberately not repeated); the unconditional-firing consumer design (§6); a fresh, isolated store never touching live production pickles (following the reward-wire audit's own §16/§17 isolation discipline); and the same separate-subprocess restart methodology `behavioral_state.py`'s own live validation already proved out. **A proposal that cannot distinguish itself from these counterfeits is not yet a learning proposal, per the mission's own standard — this report holds Approach 2 to that same standard and finds it defensible on every item except the one named repeatedly above as the single real open risk.**

## 9. The learning loop, and the longer horizon

**EXPERIENCE → OUTCOME → EVALUATION → CREDIT ASSIGNMENT → RETAINED CHANGE → RESTART/CONTEXT BOUNDARY → FUTURE BEHAVIOR → HELD-OUT TEST → NEW OUTCOME → FURTHER CHANGE**, mapped against what currently exists:

- **Experience:** strong, real, high-volume (§2).
- **Outcome:** strong for the sandbox-shaped signal (F2), weak-to-absent for everything else.
- **Evaluation:** the single weakest link project-wide, per this session's own reward-wire audit's own repeated finding — genuinely independent evaluation exists only for sandbox-checkable, deterministic-output tasks; nothing in this codebase can independently evaluate an open-ended creative or personal response at zero cost.
- **Credit assignment:** weak — RiverBrain's own dominant path credits synthesized text (§2's own dead-end finding); no mechanism anywhere cleanly attributes a validated outcome to the specific candidate/attempt that produced it, beyond the reward-wire audit's own already-noted retry-pseudo-replication risk.
- **Retained change:** real but fragmented across at least three different, incompatible schemas (RiverBrain's rolling mean, `self_model_claims.py`'s claim ledger, `behavioral_state.py`'s directive store) — §7's own "missing capability" recommendation names the fix.
- **Restart/context boundary:** solved, cleanly, at least once (`behavioral_state.py`'s own proven pattern) — this is genuinely reusable machinery, not something that needs reinventing.
- **Future behavior:** real for exactly three mechanisms (§2), all narrow.
- **Held-out test:** **fully designed, never run, anywhere, for any mechanism** — the single most consequential missing rung in the entire loop.
- **New outcome / further change:** cannot currently be assessed, because the "held-out test" step it depends on has never executed even once.

**Would repeated traversal of this loop produce measurable accumulation, or only one-shot adaptation, as currently built?** **Only one-shot adaptation, and this is not speculative — it follows directly from the missing "held-out test" rung**: without ever completing a held-out measurement even once, there is no way for this project to know whether a second traversal would add to or interfere with a first, because no traversal has ever been scored against anything but the training data itself. This is the single most important structural conclusion of this report's own loop analysis.

**Longer horizon — 10, 100, 1,000 learning episodes, for whichever approach above is pursued (forward-looking inference, clearly labeled as such):**

- **Forgetting:** LOW RISK for Approach 2's own flat, append-only store shape (nothing is ever overwritten unless explicitly requalified) — but real, unaddressed **state growth** risk, exactly the same "metabolism" problem this project has already had to solve multiple times for other logs (RETRIEVED, CLAUDE.md's own extensive Finding 51/58/59 log-retention history) — a procedure library needs the same discipline from day one, not retrofitted later.
- **Interference:** LOW-MODERATE — because each procedure is keyed to a distinct task-family signature rather than blended into one shared rolling statistic, catastrophic interference (the specific failure mode RiverBrain's own shared-mean architecture is vulnerable to, §11 of this session's reward-wire audit) is structurally less likely — but a genuinely ambiguous task family straddling two stored signatures is a real, unaddressed edge case.
- **Distribution shift:** REAL AND CERTAIN over a 100-1,000-episode horizon — any Ollama version upgrade or model-pool change (this project has already had several, per its own extensive history) could silently invalidate a stored procedure's continued relevance; **this is why a `requalification_due` field is a REQUIRED, not optional, part of any long-horizon design**, mirroring the zero-cost-ceiling adversarial review's own already-named, still-unaddressed "expiry/retest rules" gap (RETRIEVED).
- **Evaluator quality:** the ceiling here is fixed and known — F2 can only ever check deterministic-output, sandbox-executable tasks; a 1,000-episode horizon does not expand this ceiling, it only means more of the *checkable* space gets covered, never the uncheckable space (open-ended creative/personal competence remains permanently outside this report's own proposed mechanism's reach, at zero cost).
- **Credit assignment:** improves automatically under Approach 2's own design (each record is a standalone, individually-attributed validated solution, not a blended statistic) — a genuine structural advantage over Approach 1's shared-mean shape at long horizons.
- **Consolidation:** UNADDRESSED by any current design, including this report's own — at some scale, near-duplicate procedures for slightly-varied task families would need deduplication/generalization, a real, non-trivial future problem this project has already solved once for FAISS's own vector-memory pruning (RETRIEVED, `apricot-select`'s facility-location selection, this session's archaeology's own citation of the python-capability-gap audit) and could plausibly reuse.
- **Provenance:** solved by design (§7's own recommendation), if built.
- **Contradictory experience:** a real, plausible risk at scale — two validated solutions to the same task family, produced by different models at different times, might genuinely conflict in approach; no current mechanism anywhere in this codebase resolves this, and it is named here as an open design question, not a solved one.
- **Exploration/exploitation:** **completely unaddressed anywhere in FeralEcho today**, for any mechanism — nothing currently decides whether to attempt a genuinely new task family versus reusing an already-validated one, and this gap would only grow more consequential as a procedure library scales.
- **Self-generated curriculum:** real and plausible via Approach 3, but gated on first fixing the apparatus-friction problem named in that approach's own failure-mode analysis (§6).
- **Testing/requalification:** not built anywhere; a real, necessary future piece, not attempted in this report beyond naming it as required.

## 10. If FeralEcho Were My Project

1. **What would you do first?** Run §5's minimal falsification test — a P-vs-Z procedure-transfer comparison on a small, F2-checkable task family, using F2's own pass/fail as the sole oracle, before building any new infrastructure.
2. **What would you build or change?** If that test shows a real, non-null effect: build Approach 2's small, `behavioral_state.py`-shaped procedure store, keyed by task-family signature (reusing the RAOC lineage's own already-validated classifier), with F2 as the evaluator and mandatory requalification fields from day one. If it does not: pivot fully to Approach 1's cheaper, already-designed routing-learning reconnection instead.
3. **What would you stop doing?** Crediting synthesized final answers as the object of any learning signal, project-wide — credit pre-synthesis candidates instead, everywhere this pattern currently exists.
4. **What would you measure?** Not "did the store grow" and not "did a response mention the stored procedure" — specifically, held-out task pass rate, on a genuinely fresh, sealed task set, comparing the procedure-equipped arm against a matched zero-teaching arm, exactly as the frozen protocol's own already-designed EMPTY/NEUTRAL control shape specifies.
5. **What result would convince you genuine learning occurred?** A real, held-out, F2-verified pass-rate improvement for the procedure-equipped arm over the zero-teaching arm, on tasks from the same family but never previously attempted, that survives §8's full counterfeit checklist — most importantly, that is not equally reproduced by a fixed, hand-authored, generic-tip counterfeit constructed after seeing the same store's real content.
6. **What result would convince you the approach failed?** No measurable pass-rate difference between the procedure-equipped and zero-teaching arms, replicating Finding 76's own null result at a higher level of content validation — this would be genuinely informative, not merely disappointing, since it would mean the consumption problem, not the validation problem, is FeralEcho's real ceiling.
7. **What would you do next if it succeeded?** Extend the store to a second, structurally distinct task family (testing whether the mechanism generalizes beyond the first family it happened to work for), then attempt the first genuine spaced-retest (Approach 3's own longer-horizon design) on the original family, to test retention before ever claiming accumulation.
8. **What is the realistic ceiling using the current hardware and fixed local models?** Genuine, validated, same-family competence transfer for deterministic, sandbox-checkable task types, plus real (if narrow) routing/policy learning among the fixed model pool — and nothing resembling general capability growth, open-ended creative/personal competence improvement, or true accumulated competence in the strong sense, all of which remain structurally out of reach without either weight-level fine-tuning (explicitly excluded by the zero-cost constraint) or a fundamentally different, currently-nonexistent evaluation mechanism for uncheckable task types.
9. **What single idea has the greatest unexplored upside?** The shared, cross-mechanism evidence/provenance-quality layer (§7) — not because it is itself a learning mechanism, but because every future learning-shaped mechanism this project builds will otherwise keep re-inventing its own narrow, bespoke provenance scheme, exactly as RiverBrain, `self_model_claims.py`, and `behavioral_state.py` have each already done independently.
10. **Are we currently asking the right research question?** Partially. The four missions immediately preceding this one asked, in sequence, "does this specific module learn" (three times) and "can we reconnect this specific reward wire" (once) — all legitimate, well-executed, evidence-respecting questions, and this report does not retract any of their conclusions. But none of them asked the question this report opened with: **given that fixed models cannot become more capable, what is the *right kind* of "learning" for FeralEcho to pursue at all, and does the answer look like routing, or does it look like something else entirely?** This report's own answer — that the right target is validated, portable, context-based competence, not routing and not weight change — is a genuinely different research direction from where the last several missions' own momentum was heading, and this report recommends adopting it, provisionally, pending §5's own cheap, fast, honest first test.
