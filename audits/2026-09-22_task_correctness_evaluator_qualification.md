# Task-Correctness Evaluator Qualification

Read-only. Git HEAD `2fba42644c82b9f7096276f4dd338d615cf1bcce` unchanged before and after (confirmed by direct `git rev-parse` before and after this investigation). No new task set was built; nothing was run. This document only inspects existing code and existing artifacts.

## 1. Executive verdict

None of the three originally-named candidates was assumed suitable, and independent inspection changed the picture: two of the three (`objective_verify`, `verify_response_code`) are thin, correctly-scoped wrappers around one real mechanism, not independent evaluators in their own right — `verify_response_code` in particular is disqualified outright for this purpose, for a reason specific to its own design, not a minor gap. `oracle_runner.grade()` is a real, sound, hidden-test evaluator, and it is not the strongest thing in the repository for this job. **The single best-qualified existing machinery is not one of the three named candidates — it is the AP-0 v2 apparatus (`worlds.py` + `tasks_v2.py` + `jail.py` + `freeze.py` + `oracle_b_v2.py`), which already implements procedurally-novel task generation, mutant-killing hidden-test construction, OS-level (not just prompt-level) leakage prevention, and cryptographic pre-registration — everything this mission's own checklist asks for, built for a different, earlier mission but not tied to it.** `oracle_runner.grade()` is the correct grading primitive to reuse (AP-0 itself already reuses it); the task-authoring and leakage-control layer around it is what actually answers "did the generator solve this on information unavailable to it," and that layer already exists too, in AP-0's own `tasks_v2.py`/`worlds.py`, not in `run_capability_pilot.py`'s fixed 15-task suite. **Hidden task correctness is AVAILABLE, not merely partial** — but only if the rescued experiment reuses AP-0's construction, not the capability-pilot's frozen suite as-is, for a reason given in §7/§9 below (that suite's own tasks are common, memorizable, textbook-shaped problems with no procedural novelty, and this session alone has already run them dozens of times across three prior tiers of research — a real prior-exposure risk `worlds.py`'s pseudo-word convention design was built specifically to close).

## 2. Candidate evaluator architecture

All three candidates, and AP-0's own grader, converge on the identical low-level primitive: concatenate candidate code + test code into one script, run it inside `sandbox-exec` via `sandbox/safe_exec_wrapper.py` (or a thin reimplementation of the identical invocation), and check stdout for a specific marker string. What differs between them is entirely in the layer *above* that primitive: what the test code asserts, whether the marker can be guessed or memorized, and whether the test code is ever exposed to the generator. That layer, not the sandbox call, is where correctness as a metric is actually established or fails to be.

## 3. `oracle_runner.grade()` analysis

Source: `app/experiments/accumulation_probe/oracle_runner.py`. Own module docstring states it deliberately reimplements `run_sandbox_script_isolated`'s invocation "WITHOUT importing it (its import has file-writing side effects)" — a real, disclosed reuse-vs-reimplementation tradeoff, not an oversight.

1. **What exact artifact/input does it grade?** `grade(candidate_code, test_code)` — arbitrary Python source concatenated with a test script; `extract_code()` (a separate function in the same file) pulls candidate code out of raw model text first, by a pre-registered rule (last fenced block defining the target function name, else last fenced block, else raw text if it contains `def`).
2. **What does it actually execute or inspect?** Real execution, not import-only — `run_script()` writes the combined source to a temp file and runs it as a real script inside the kernel sandbox (`sandbox-exec -f echo_sandbox.sb`), then checks the subprocess's actual stdout.
3. **Where does ground truth come from?** `test_code` is caller-supplied — `grade()` itself has no opinion about correctness; it is a pure execution+marker-check primitive. Ground truth quality is entirely a property of whoever builds `test_code`, not of this function.
4. **Are tests hidden from generation?** Not by this function's own design — `grade()` doesn't touch generation at all. Hiddenness is a property of the caller (confirmed real, at the OS level, in AP-0's own `jail.py`, see §7).
5. **Could the generator infer or retrieve the answers?** Not from anything in `grade()` itself. The nonce mechanism is real and effective for its narrow purpose: `nonce = secrets.token_hex(8)` is generated fresh, after generation, and substituted into `test_code` via a `@@NONCE@@` placeholder — a candidate cannot pre-print the exact pass string (`"ALL_TESTS_PASSED_" + nonce`) because the nonce doesn't exist yet when the candidate is generated. This closes exactly one gaming vector (hardcoding the success marker) and no others — it says nothing about whether the *test assertions themselves* are guessable, which depends entirely on what `test_code` the caller supplies.
6. **Does it measure semantic task correctness?** Only as strong as the supplied test suite. `grade()` provides no test-authoring guidance or safeguard against a weak test suite on its own.
7. **Is scoring deterministic?** Yes, modulo real sandbox infrastructure flakiness (timeout, a `sandbox_apply`-class error) which is explicitly classified separately (`infra: True/False`) rather than conflated with a genuine task failure — a real, disclosed design choice that matters for clean statistics.
8. **Can it grade structurally novel task instances?** Yes, trivially — it has no opinion about the task at all, only about whether a marker string was printed.
9. **Can evaluation remain independent of learning/selection?** Yes — `grade()` has no side effects beyond running a subprocess and returning a dict; it does not log, does not touch RiverBrain, does not persist anything.
10. **Can it run cheaply and locally?** Yes — one subprocess per grade call, no network dependency beyond what the candidate/test code itself might do (none in AP-0's real tasks).
11. **Can it support a frozen chronological experiment?** Yes, and AP-0 already uses it this way — `freeze.py` hashes the full artifact set (including this file) before any real model call, so the grading code itself is part of what gets frozen.
12. **What leakage paths exist?** None from `grade()` itself. All real leakage risk lives in what `test_code` contains and how it reaches (or fails to reach) the generator — a caller responsibility, not a flaw in this function.
13. **What existing task corpus can feed it?** AP-0's own `worlds.py`/`tasks_v2.py` pipeline (see §8) already produces `test_code` in exactly the shape `grade()` expects, has done so for a live, in-progress mission, and is running as of this investigation (background AP-0 dev/qual jobs are currently mid-flight in this same session).
14. **What changes would be required to use it?** None to `grade()` itself. A rescued experiment would need its own frozen task set (§9) and its own generation-side isolation (already solved in this repo, see the reconciliation report's §8/Tier-8 finding), but the grading primitive is directly reusable as-is.

## 4. `run_capability_pilot.objective_verify()` analysis

Source: `scripts/run_capability_pilot.py`. **This is not an independent evaluator — it is a two-line wrapper that reimports and calls `code_verification.verify_in_sandbox()`, the exact same low-level sandbox-execution function `verify_response_code()` uses.** It does not implement grading logic of its own.

1. **What exact artifact/input does it grade?** `candidate_code + "\n\n" + test_code`, run as one script — mechanically identical to `oracle_runner.grade()`'s approach, but with a fixed, non-nonced marker string (`"ALL_TESTS_PASSED"`).
2. **What does it actually execute or inspect?** Real execution via `verify_in_sandbox()` → `run_sandbox_script_isolated()` (the production sandbox entry point, not a reimplementation) — stdout is checked for the fixed marker.
3. **Where does ground truth come from?** Caller-supplied `test_code`, same as `oracle_runner.grade()` — in `run_capability_pilot.py`'s own real use, this is `task["test_code"]` from `audits/capability_pilot/task_suite.json`, a genuinely frozen, hash-verified 15-task suite (`main()` asserts the file's sha256 before running).
4. **Are tests hidden from generation?** In the capability-pilot's own real usage, yes at the prompt level — `task["prompt"]` (what the generator sees) and `task["test_code"]` (what grades it) are separate fields, and nothing in the three generation conditions (`run_condition_a_raw`/`b_pipeline`/`c_council`) ever passes `test_code` into a prompt. But this is a property of how the pilot script *uses* the task file, not a property `objective_verify()` itself enforces or could enforce — nothing stops a future caller from accidentally leaking `test_code` into a prompt, the same way nothing in `grade()` would either.
5. **Could the generator infer or retrieve the answers?** **Real, unaddressed gap, distinct from anything `oracle_runner.grade()` has**: no nonce. The fixed string `"ALL_TESTS_PASSED"` can be hardcoded by a generator that has ever seen this exact evaluator's convention (in training data, in a prior session's own generated code that happened to include a `print("ALL_TESTS_PASSED")` line, or via retrieval from this project's own accumulating logs, which is precisely the mechanism a persistent-learning experiment is trying to test). This is a real, structural weakness for this specific mission's purpose — not disqualifying on its own (a nonce could be added), but it is not currently present, and the mission's own §5 explicitly names "exploit deterministic fixtures" as an attack to check for.
6. **Does it measure semantic task correctness?** Same answer as `oracle_runner.grade()`: only as strong as the supplied `test_code`. `run_capability_pilot.py`'s real 15-task suite uses plain `assert` statements with concrete example inputs/outputs (confirmed by direct read, e.g. `assert dedupe_preserve_order([1,2,2,3,1,4]) == [1,2,3,4]`) — a handful of hand-picked examples, not a systematically-constructed mutant-killing test set. This is weaker test-authoring than AP-0's own `make_cases2()` (§8), though it is real, executable, and does check actual behavior, not just import success.
7. **Is scoring deterministic?** Yes, same infrastructure-flakiness caveat as above, though `objective_verify()` itself does not separately classify infra failures the way `oracle_runner.grade()` does (`ran_ok` is the closest analogue, conflated with genuine non-pass in the returned dict's shape).
8. **Can it grade structurally novel task instances?** Yes, mechanically — same answer as `grade()`. But the *existing* task suite behind it (§8) is not structurally novel per-instance the way AP-0's procedurally-generated tasks are; each of the 15 tasks is one fixed instance, not a template that generates fresh instances per run.
9. **Can evaluation remain independent of learning/selection?** Yes for the function itself. `run_capability_pilot.py`'s own surrounding script goes further and actively engineers this independence for its own RiverBrain-adjacent concerns (`install_isolation()`, the read-through/write-blocked proxy) — real, substantial isolation engineering that is directly reusable (and, per the reconciliation report's §8, already the proven fix for the Tier-8 background-writer-thread gap).
10. **Can it run cheaply and locally?** Yes, identical to `grade()`.
11. **Can it support a frozen chronological experiment?** Yes — the script's own `main()` already enforces a hash-pinned frozen task suite before it will run at all, a real, working precedent for exactly this requirement.
12. **What leakage paths exist?** The missing-nonce gap above (§5) is the concrete one. A second, disclosed-in-source leakage risk: `run_capability_pilot.py`'s own condition B calls `generate_code_from_plan()` with the task's prompt as the self-edit "plan" argument — this routes through self-edit's real prompt-assembly, which (per the reconciliation report's §6) can inject `initial_f2_error` evidence from the attempt ledger. That's not a leak of *this task's* hidden test, but it is a real, unaccounted-for extra information channel available to one condition and not others if this script were reused verbatim for a learning experiment without controlling for it.
13. **What existing task corpus can feed it?** The 15-task `audits/capability_pilot/task_suite.json` suite, real and hash-frozen, but small, fixed, and (per §9) already heavily exposed within this project's own research history.
14. **What changes would be required to use it?** Add a nonce (trivial, mirrors `oracle_runner.grade()`'s own already-solved pattern) if reused; otherwise, no code change required to call it, but the task corpus behind it needs replacing or supplementing per §9.

**Verdict on this candidate specifically: it is not a distinct evaluator, it is `code_verification.verify_in_sandbox()` plus a fixed marker string, real and usable, but weaker than `oracle_runner.grade()` on the one axis (gaming resistance) that matters most for a persistent-learning experiment specifically, and it carries this repository's own already-demonstrated capability-pilot corpus, which is a liability, not an asset, for a fresh confirmatory run (§9).**

## 5. `code_verification.verify_response_code()` analysis

Source: `app/core/code_verification.py`. Read in full, including its own module docstring, which states its scope with unusual precision: *"this does not attempt to prove arbitrary generated code is 'correct' in general... it catches two concrete, bounded things: (a) code that doesn't even parse, and (b)... a response that contains its own checkable claim... that turns out to be false when actually run. That second part is narrow by design — it catches self-contradiction, not general incorrectness."*

1. **What exact artifact/input does it grade?** A full conversational response's text, not a candidate/test pair. It extracts fenced code blocks and, separately, a *self-claimed* worked example (`find_claimed_example()`: a `print(...)` call followed by a claimed `# Output: ...` comment or trailing comment).
2. **What does it actually execute or inspect?** Real execution via `verify_in_sandbox()`, but **only when the response itself makes a checkable claim.** If `find_claimed_example()` returns `None` — the common case for most coding answers, by the function's own docstring — nothing is ever executed, and the function returns `(None, None)`.
3. **Where does ground truth come from?** **This is the disqualifying structural fact.** Ground truth is *the generator's own claimed output*, not an independently authored expected result. `verify_response_code()` checks whether the generator's code is *internally consistent with what the same generator said it would print* — it has no external oracle at all.
4. **Are tests hidden from generation?** Not applicable — there is no separate hidden test. The "test" (the claimed output) is authored by the generator itself, as part of the same response being graded.
5. **Could the generator infer or retrieve the answers?** Trivially, always — the generator wrote the claim being checked. A generator that never makes a checkable claim (returns no `print(...)`/`# Output:` pair) is unconditionally unscoreable (`verified=None`), and a generator that always makes trivially-true claims (e.g., claims exactly what its own code would actually print, without needing to reason about correctness at all) would score `verified=True` while having demonstrated nothing about task correctness.
6. **Does it measure semantic task correctness?** **No.** It measures self-consistency between a claim and its own execution — a real, useful, narrow property (catching confabulated "worked examples," per this module's own origin story, Finding #1 of the 2026-07-18 self-awareness audit) but categorically different from "did this solve the intended task," which requires an *externally specified* expected behavior the generator never gets to author.
7. **Is scoring deterministic?** Yes, when a claim exists to check.
8. **Can it grade structurally novel task instances?** Not meaningfully — since the "test" is generator-authored, there is no external task specification for a novel instance to be measured against at all.
9. **Can evaluation remain independent of learning/selection?** Yes mechanically (pure function, sandboxed execution, no side effects) — but independence of the *execution mechanism* doesn't rescue the *ground-truth* problem in §3/§6.
10. **Can it run cheaply and locally?** Yes.
11. **Can it support a frozen chronological experiment?** Not as a correctness measure — there is nothing to freeze in advance, since the "expected output" doesn't exist until the generator invents it at generation time.
12. **What leakage paths exist?** None in the conventional sense (no hidden test to leak) — but this is exactly why it fails the mission's core question rather than an accidental leakage gap.
13. **What existing task corpus can feed it?** None applicable — this function does not consume an external task/test corpus at all; it operates on free-form conversational responses.
14. **What changes would be required to use it?** None would make this evaluator answer the mission's core question — its fundamental design (self-claimed, not externally-specified, ground truth) is incompatible with "solved the task on information unavailable to the generator," not merely under-equipped for it. This is a scope mismatch, not a gap to close.

**Verdict on this candidate specifically: NOT QUALIFIED, and not qualifiable by extension — it answers a genuinely different, narrower, useful question (self-consistency / confabulation detection) that this project's own module docstring already states honestly. Using it as a stand-in for task-correctness would silently substitute "didn't contradict itself" for "solved the task," which is exactly the kind of claims-ladder rung-jump this mission and the reconciliation report both exist to prevent.**

## 7. Leakage analysis

Two independent leakage layers exist across the candidates, and they are not equivalent:

- **Prompt-level leakage** (does the task/system prompt contain the hidden test or its literals?): all three candidates rely on the *caller* to keep test code out of the prompt. None of the three functions themselves enforce this. `run_capability_pilot.py`'s own `main()` keeps `task["prompt"]` and `task["test_code"]` in separate fields and never concatenates them into a request — a real, working discipline, but a caller convention, not a mechanical guarantee.
- **OS-level leakage** (can the generation process, or anything it spawns, *read* the hidden test / oracle / worlds file from disk, regardless of what's in the prompt?): **only AP-0's `jail.py` addresses this layer at all.** Its Seatbelt profile (`(deny file-read* (subpath "{exp}"))(allow file-read* (subpath "{arm}"))`) makes it structurally impossible for a generation-arm process to read the experiment root (where hidden tests, worlds, and the oracle live) even if a prompt-construction bug accidentally tried to reference a path there — a genuinely stronger leakage control than "we checked the prompt doesn't contain it," which is the ceiling of what the other two candidates' surrounding scripts provide. `qual.py`'s own `scan_leaks()` function additionally does a real, automated literal-scan check (`assert not leaks, f"hidden VAL literal present in constructor requests..."`) as a second, independent, mechanical check on top of the OS-level jail — belt-and-suspenders, not either/or.
- **Marker/answer guessability**: `oracle_runner.grade()`'s nonce closes the "hardcode the pass string" vector; `objective_verify()`'s fixed marker does not. Neither addresses whether the *test assertions* themselves could be memorized from a prior exposure to the same literal task — which is why §9's frozen-task-set feasibility section treats the capability-pilot's own fixed suite as a liability for a fresh confirmatory run specifically (this session, and prior sessions, have already run those exact 15 tasks through multiple conditions across Tier-3 through Tier-5 — real prior exposure, not hypothetical).
- **Evaluator-trace leakage into retained experience** (the mission's own "independence" question, §10 below): none of the three evaluators log anything by default; whether a rescued experiment's *harness* accidentally forwards a failure diagnosis or hidden-test detail into a retained-experience channel is a harness design question, not a property of `grade()`/`objective_verify()`/`verify_response_code()` themselves.

## 8. Existing task-corpus options

Two real, independent corpora exist, at very different levels of rigor:

**Option A — `run_capability_pilot.py`'s frozen 15-task suite** (`audits/capability_pilot/task_suite.json`, sha256-pinned). Real, hash-verified, already proven usable end-to-end across Tier-3/4/5 (per the reconciliation report). Each task is a single fixed instance (e.g., `dedupe_preserve_order`) with a handful of hand-picked `assert` cases — no procedural generation, no structural novelty per run, and (critically for a *learning* experiment specifically) this exact suite has already been used, by this exact project, across dozens of real generations in prior missions. Reusing it for a persistent-learning confirmatory run risks the generator (or a retained-experience mechanism) having genuinely seen these specific tasks before, which would confound "did it learn a general skill" with "does it recognize this specific, previously-encountered problem" — precisely the memorization confound the mission's own §5 asks to rule out.

**Option B — AP-0 v2's `worlds.py` + `tasks_v2.py` pipeline.** Built for a different mission (accumulation-probe, testing whether a model can pick up an in-context "world convention" and apply it), but the machinery is task-content-agnostic and directly reusable:
- `worlds.py` generates fresh, non-dictionary pseudo-word tokens per run (`pseudo_word()` explicitly checks candidates against a real system dictionary and rejects real-word collisions) — genuinely novel surface content per seed, not a fixed literal task.
- `tasks_v2.py` provides **T** (base template), **S** (surface-variant, e.g. same logic over a different input shape — tuples instead of dicts, a parsed string instead of structured data), **NEAR** (plausible-but-different task sharing vocabulary), and **UNREL** (unrelated control) splits — already the exact T/S/NEAR/UNREL taxonomy the mission's own §"Frozen task set" section describes wanting, built and working before this mission was ever posed.
- `make_cases2()` builds hidden test cases by a real adversarial process: generate a large candidate-input pool, compute a reference solution's output for each, compute which of a large hand-authored + auto-generated mutant set each candidate input would catch, then greedily select a minimal case set that kills every non-equivalent mutant — checking mutant *equivalence* on 4,000 extra random inputs rather than assuming a mutant that survives greedy selection is truly equivalent. This is meaningfully stronger test-authoring than either `objective_verify()`'s or `oracle_runner.grade()`'s own real-task usage today (both currently rely on hand-picked example asserts, not mutant-killing coverage) — though it is *available to* both, since it only produces `test_code` strings in the same shape `grade()`/`objective_verify()` already consume.
- `oracle_b_v2.py` is a second, independently-written reference implementation (different idioms — `functools.cmp_to_key`, `itertools.accumulate`, `Counter`, vs. the primary reference's more direct loops) used to cross-check the primary oracle for bugs — a real, working instance of exactly the "who grades the grader" concern any hidden-test evaluator has to answer.
- `freeze.py`/`qual.py`'s `freeze_qual()` cryptographically hash-pin the entire artifact set, the model digest, the preregistration text, and every decision constant (`GATE_MIN_PASS`, `Q_EXACT_QUALIFIED`, etc.) *before* any real generation call, and `write_json_new()` refuses to overwrite an existing frozen file — real, load-bearing immutability, not a documentation convention.
- `jail.py` — see §7 — is the one piece of this apparatus with no analogue anywhere in the other two candidates' surrounding infrastructure: OS-level read confinement for the generation process itself.

**Honest caveat, not glossed over: this apparatus is not currently a finished, ready-to-hand-off task set.** As of this investigation, AP-0's own v2 dev-calibration and qual-gate phases are still running in this same session (background tasks confirmed active) — the T/S template *qualification* (which templates make the cut per the dev-H pass-rate rule) is mid-flight, and there is no already-built, already-frozen "confirmatory/holdout" task file for a *different* experiment to simply import today. What's reusable is the **machinery** (worlds/tasks_v2/jail/freeze/oracle_b_v2), proven to work end-to-end on a live mission, not a pre-packaged corpus. Building a frozen task set for the rescued learning experiment would mean pointing this same machinery at a fresh set of task templates (or reusing AP-0's own qualified T/S templates once that mission concludes, if the underlying skill domain — small pure Python functions over structured data — is judged suitable), not writing a new construction pipeline from scratch.

## 9. Frozen task-set feasibility

**FEASIBLE**, using Option B's machinery, **NOT yet built** as a ready artifact for this specific mission. The concrete needs (development tasks, prospective tasks, untouched holdout tasks, structurally related but non-identical instances, hidden expected behavior, no answer leakage into generation) map directly onto pieces that already exist and already work:

| Requirement | Existing mechanism |
|---|---|
| Development tasks | AP-0's `T1`/`T2` base template registries + a chosen `worlds.py` seed for development |
| Prospective test tasks | A second, disjoint `worlds.py` seed (already how AP-0 separates `dev` from `qual` namespaces — `qual.py`'s `qworlds()` uses `MASTER_SEED + 7000 + ...`, a deliberately separate offset from dev's own seed range) |
| Untouched holdout tasks | A third, never-yet-drawn seed range, held back until a confirmatory run — no such file exists yet, but the seeding mechanism trivially supports it |
| Structurally related but non-identical instances | `tasks_v2.py`'s S/NEAR splits, by construction — same underlying skill, different surface shape |
| Hidden expected behavior | `make_cases2()`'s mutant-killing case construction, real and working |
| No answer leakage into generation | `jail.py`'s OS-level confinement + `qual.py`'s `scan_leaks()` literal-scan, both real and both already exercised in this exact repository |

**What would need to change**: the task *domain* (AP-0's tasks are about applying an in-context "world convention," not about accumulated general coding competence) may or may not be the right domain for a persistent-learning experiment — this is a genuine open design choice, not a solved problem. The reusable part is the *construction and freezing machinery*, not necessarily AP-0's specific K1/K2/K3 conventions themselves, though nothing here rules those out as a valid starting domain either.

## 10. Evaluator independence

Separating, as instructed, **score/outcome available for learning** from **hidden evaluator evidence unavailable to learning**:

- All three evaluators return, at minimum, a boolean pass/fail (`passed`) — this is the minimal, legitimate outcome signal a learning mechanism should be allowed to see. None of the three, by default, expose the hidden test's literal assertions or expected values in their return dict.
- **Real, disclosed risk, not hypothetical**: `oracle_runner.grade()` returns `output_tail`/`error_tail` (last 300 chars of stdout/stderr) and `objective_verify()` returns `output_tail` (last 800 chars). For a failing candidate whose error message happens to echo part of the test assertion (a common Python failure mode — an `AssertionError` can print the compared values), **this tail could leak a fragment of the hidden expected output** into whatever consumes the grade dict. This is not a flaw in the grading functions themselves (truncated diagnostic tails are a reasonable, useful thing for a human-facing report to have) — it is a real hazard specifically *if* a rescued experiment's harness naively forwards the full grade dict into a retained-experience channel rather than deliberately extracting only the boolean outcome (and, if wanted, a coarse failure-class label) the way the reconciliation report's §6 already requires ("exactly one defined policy reward... labeled separately" / "hidden evaluator evidence unavailable to learning").
- `code_verification.verify_response_code()` has no equivalent because it has no hidden test to leak (§5) — its risk is a different one (self-authored ground truth), not an evidence-leak one.
- **Concrete design requirement for the rescued experiment, derivable directly from this**: the harness must explicitly define a narrow "learning signal" extraction (pass/fail, maybe a coarse failure-class enum) from whichever evaluator's dict is used, and must never forward `output_tail`/`error_tail`/the raw `test_code` itself into whatever channel the experimental condition's retained state reads from. This is not automatic — it would need to be built deliberately, the same way `_attempt_ledger_evidence_section()`'s narrow, by-name field extraction is deliberate (reconciliation report §6).

## 11. Adversarial attack

Worked through the mission's own attack list against each real candidate, not just in the abstract:

- **Memorize visible tests?** Not applicable to hidden-test evaluators (`grade`, `objective_verify` as used) by construction, since the test is never shown. Directly applicable, and fatal, to `verify_response_code()` — there is no "hidden" test to memorize because the generator authors the check itself (§5).
- **Exploit evaluator structure?** `objective_verify()`'s fixed, un-nonced marker string is a real, concrete exploit surface: a generator (or a retained-experience mechanism that has seen this project's own prior evaluator output) could learn to always emit `print("ALL_TESTS_PASSED")` as a hedge, independent of whether the rest of the code is correct, if the test code itself has any code path that reaches that print regardless of assertion outcomes — or, more realistically, if a future harness bug ever runs the marker print before the assertions rather than after. `oracle_runner.grade()`'s nonce specifically forecloses the cheapest version of this attack (a hardcoded pass string can never match a nonce it can't know in advance).
- **Produce hard-coded outputs?** Real risk for the fixed 15-task suite (Option A, §9) specifically because those exact tasks and their exact `assert` literals are already visible in this project's own git history and audit files (`audits/capability_pilot/task_suite.json` itself is a checked-in, readable file) — a generator or retrieval mechanism with access to this repository's own content (which self-edit's own generation context plausibly has, via project-file context injection) could recover the expected outputs directly, without ever "solving" anything. AP-0's procedurally-generated worlds (Option B) are specifically designed to resist this: the pseudo-word tokens and the specific input/expected pairs are freshly drawn per seed and never checked into a stable, readable file until `freeze.py`'s post-hoc archival — and even then, a fresh holdout seed drawn *after* freezing remains genuinely unseen.
- **Recognize task IDs?** A real, named risk in `tasks_v2.py`'s own comments (task IDs like `k1_sumcat`, `K1.T5` are internal bookkeeping, never exposed in the rendered `spec` text sent to a generator — confirmed by reading `build_tasks_v2()`, which renders `spec` from natural-language template strings, not from the ID). The 15-task capability-pilot suite's task IDs (e.g., `dedupe_preserve_order`) are literally the function names requested in the prompt — not a distinguishing risk on their own, but worth noting these are common, recognizable, textbook-style names, unlike AP-0's deliberately non-dictionary pseudo-word conventions.
- **Access expected answers?** Only via the OS-level jail's absence — this is precisely why `verify_response_code()`/`objective_verify()`'s underlying `run_capability_pilot.py` script relies on prompt-construction discipline alone (real, but weaker) while AP-0's `jail.py` makes it structurally impossible for the generation process itself to open the hidden-test file regardless of what the prompt contains.
- **Exploit deterministic fixtures?** The un-nonced `"ALL_TESTS_PASSED"` marker in `objective_verify()` is exactly this — a deterministic fixture a sufficiently informed generator or retained-experience signal could exploit. `oracle_runner.grade()`'s nonce closes it.
- **Pass without solving the intended task?** Confirmed structurally possible for `verify_response_code()` (self-authored claims can be trivially true without the underlying code being generally correct) — this is the clearest, cleanest disqualification in this whole investigation, not a probabilistic risk but a design-level certainty.

## 12. Recommended evaluator

**`oracle_runner.grade()`, fed by AP-0's `worlds.py`/`tasks_v2.py`/`jail.py`/`freeze.py` construction pipeline, is the recommended combination — one existing grading primitive plus one existing construction/leakage layer, not an assembled patchwork of unrelated pieces.** This is not "pieces of multiple evaluators" in the sense the mission asks to avoid; `oracle_runner.grade()` and AP-0's task-construction modules already live in the same package (`app/experiments/accumulation_probe/`), are already used together for AP-0's own real, currently-running mission, and were not built independently of each other. `objective_verify()` is a reasonable fallback if AP-0's construction layer is judged out of scope to adapt (it reuses the identical underlying sandbox call and the identical concatenate-and-run shape), but it should gain a nonce before use, and its existing task corpus (Option A) should not be reused verbatim for a learning experiment given this project's own prior exposure to it. `verify_response_code()` is not recommended for any role in a task-correctness measurement — its self-authored-ground-truth design answers a different, narrower, legitimate question that this project's own module docstring already states plainly, and using it here would be a scope mismatch, not a shortcut.

## 13. Minimum prerequisites

1. Decide the task domain for the rescued experiment's frozen corpus (reuse AP-0's K1/K2/K3 convention-application skill, or author a new small domain in the same T/S/NEAR/UNREL shape) — a real design decision, not assumed here.
2. Draw a fresh, disjoint `worlds.py` seed range for the learning experiment specifically, separate from AP-0's own dev/qual/(future holdout) seeds, so the two missions' frozen material never overlaps.
3. Build dev / prospective / holdout task splits using `tasks_v2.build_tasks_v2()` + `make_cases2()`, freezing via `freeze.py`'s pattern before any real generation call.
4. Wrap generation in `jail.py`'s Seatbelt confinement, scoped to each experimental arm's own root, exactly as AP-0 already does.
5. Grade with `oracle_runner.grade()`, unmodified.
6. Build the narrow evidence-extraction layer named in §10 (pass/fail + coarse failure class only) between the grade dict and whatever the experimental condition's retained state consumes — this does not exist yet anywhere in this repository and is real, if small, new work.
7. Everything else required for the rescued experiment (the fixed contextual-routing comparator, the isolated-harness RiverBrain-redirection pattern, matched compute budgets) is already specified in the reconciliation report's §9 and is independent of which evaluator is chosen.

## 14. Remaining unknowns

- Whether AP-0's K1/K2/K3 convention-application skill domain is a *good* domain for measuring general coding-competence accumulation, versus a domain that happens to have excellent construction machinery already built for an unrelated question — UNKNOWN, a real design judgment not resolved by this investigation.
- Whether `make_cases2()`'s mutant-killing test construction generalizes cleanly to a task domain outside K1/K2/K3's specific shape (dict/list/string transformations over small structured records) without significant rework — UNKNOWN, not tested here.
- Whether AP-0's own qualification gate (currently running in this same session) will conclude that few enough T/S templates survive to leave a usably-sized frozen corpus for a *second*, unrelated experiment to draw from — UNKNOWN, genuinely in progress as this report is written.
- Whether the narrow evidence-extraction layer (§10, §13 item 6) can be built without any unintended path for hidden-test content to reach a retained-experience channel — PROPOSED here as a requirement, not yet verified against a real implementation, because none has been built.

## 15. Final recommendation

Do not build a new evaluator. Do not use `verify_response_code()` for this purpose under any adaptation. Reuse `oracle_runner.grade()` as the grading primitive, and reuse AP-0's `worlds.py`/`tasks_v2.py`/`jail.py`/`freeze.py` pipeline as the frozen-task-construction and leakage-prevention layer, pointed at a fresh, disjoint seed range specific to the learning experiment. This closes the missing piece the reconciliation report's §3/§9 flagged as the one remaining blocker to a rescued, interpretable experiment — not by inventing new infrastructure, but by recognizing that the needed infrastructure already exists, already works, and was simply never connected to this question.
