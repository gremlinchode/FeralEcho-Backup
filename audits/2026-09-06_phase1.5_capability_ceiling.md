## 1. Executive Conclusion

FeralEcho is a real, continuously-running, locally-hosted multi-model system with genuine, demonstrated
persistence and a real, working recovery capability — proven tonight by an actual incident, not staged.
It has a large, genuinely sophisticated self-observation apparatus (the Liveness Ledger, 30 functional
canaries) with a real track record of catching regressions across this project's multi-month history.

It does **not** currently have a demonstrated, closed self-improvement loop. The single clearest,
most-corroborated finding across every investigation leg tonight — reached independently by at least
four separate lines of evidence (Phase 0's direct reward-signal trace, Phase 1/1A's functional-verifier
work, the Findings-91-93 forensic pass's correlation analysis, and this session's own earlier
capability-ceiling research) — is that the signal driving self-edit's targeting and deployment
decisions is structurally blind to whether generated code actually works. The mechanism that *should*
close this loop (real sandboxed execution, real human ratings) exists, runs continuously, and is
**structurally disconnected** from the decision it would need to influence. This is not a vague
architectural worry — it is directly proven by source code (§4).

## 2. Current Causal Architecture

For the subsystems where a full `INPUT → PROCESSING → STATE CHANGE → DOWNSTREAM CONSUMER →
BEHAVIORAL EFFECT` chain is fully provable:

- **Conversational model selection**: user message → `detect_task_type()` → `rank_models()`/
  `_select_council()` read `model_task_stats` → a specific model is chosen → response generated →
  `.learn()` writes a new observation back into `model_task_stats` → **next** selection reads the
  updated value. **Fully closed, fully proven** `[inherited: Phase 0, re-confirmed this pass via §4]`.
- **Self-edit targeting**: real outcome history → `SelfModelUpdater.get_weak_task_type()` →
  `perform_self_edit()` targets that task type → candidate generated → F1/F2/F3 + AST fitness gate →
  deploy or reject → outcome tracked. **Closed at the targeting level, broken at the evaluation level**
  — the "evaluate" step never touches whether the code works (§4, §9).
- **Recovery**: process death → watchdog detects (10s poll) → restart → sentinel reaches `serving` →
  liveness ledger confirms health. **Fully closed, and empirically exercised tonight** — a real
  terminal-freeze/connectivity-loss incident during this session, recovered exactly as designed.
- **Memory retrieval → response**: a turn's content → embedding → FAISS top-k retrieval → injected into
  the next prompt → shapes the response. **The mechanical chain is proven; whether it changes the
  response in a way distinguishable from noise is not** — Finding 76 (this session, memory-ablation
  experiment, `audits/2026-09-23_memory_ablation_experiment.md`) found the control-vs-ablation embedding
  distance distribution (mean 0.304, n=30) statistically indistinguishable from the pure sampling-noise
  floor (mean 0.254, n=5; p=0.48/0.37) on the `personal`/direct-response path specifically. **This is
  the single most important nuance this synthesis adds to the "does memory work" question: the pipe is
  real, the measured behavioral effect is not established.**

## 4. RiverBrain Topology — Resolved Precisely, This Pass

Direct source read of all four `.learn*()` methods in `echo_model_orchestrator.py`, plus
`learn_from_council_rating()` (a fifth, found during this resolution — not previously enumerated as a
separate pathway in this session's prior context):

| Pathway | Observes | Label/reward | Writes `classifiers`/`scalers` | Writes `model_task_stats` (the signal selection actually reads) | Real downstream behavioral effect |
|---|---|---|---|---|---|
| `.learn()` (line 808) | Every real conversational + self-edit-generation response | `_score_response_quality()` — **AST structure only**, proven blind to correctness (Phase 0/1) | Yes | **Yes** | **Yes — this is the only pathway that reaches real model selection on its own** |
| `learn_from_council_rating()` (line 936) | Peer/council ratings, gated `is_council_trusted()` | Blended council+quality score | Yes | **Yes** | **Yes** — a second, real, functioning contributor |
| `learn_from_sandbox_outcome()` (line 870) | Self-edit's own **real** sandbox pass/fail — genuine behavioral ground truth | 1/0 on real success | Yes (trains the classifier) | **No — confirmed by direct read, zero reference anywhere in the function** | **No.** `sandbox_observation_counts` (its only other write) is confirmed, by direct grep, to be read only for a log line (`echo_model_orchestrator.py:1092`) — never for a decision. |
| `learn_from_rating()` (line 898) | **Real, explicit human 1-5 ratings** — CLAUDE.md's own docstring calls this "a high-trust learning signal," 3x-weighted | 1/0 on rating | Yes (3x-weighted) | **No — confirmed by direct read, zero reference anywhere in the function** | **No.** |

**The classifier itself, trained by all five/four pathways combined, has exactly one live consumer of
its predictions anywhere in the codebase** (`.learn()`'s own `predict_one()` call, line 821) — and that
consumer's only purpose is feeding `accuracy_trackers`, which §3 already established is itself a dead
end. **This means: real sandbox pass/fail outcomes and real explicit human ratings currently have zero
verified effect on any future decision in this system, direct or indirect.** They are computed,
persisted, and then structurally discarded by the topology itself — not by any single bug, but by the
simple fact that nothing downstream of the classifier they train ever gets read for a purpose that
matters. Model selection is driven by exactly two live signals: an AST-heuristic proxy for coding
quality, and peer/council conversational ratings. This is a materially more precise and more
consequential finding than "two of four pathways don't feed `model_task_stats`," which is how this
session characterized it earlier tonight before this resolution — that earlier framing undersold the
`learn_from_rating()` half of the finding specifically (human ratings, described in this codebase's own
comments as "high-trust," are just as disconnected as the automated sandbox signal).

## 7. Digital-Organism Property Analysis

Evaluated honestly, not forced into the metaphor:

- **Persistence**: applies well. Direct evidence, §6.
- **Homeostasis**: applies well — `system_guard.py`'s RAM throttle, MLX crash avoidance (which
  genuinely engaged and disengaged based on real crash clusters, `[inherited: CLAUDE.md's documented
  history]`), and log-retention rotation are all real, self-regulating mechanisms with demonstrated
  live activity (rotation events, avoidance state) — not just designed-but-idle code.
- **Metabolism**: applies partially. The system continuously consumes compute and transforms
  interaction into persisted state — but §3–§4 establish that a real fraction of that "metabolized"
  state (`accuracy_trackers`, the sandbox-outcome/rating classifiers) is never used again. A metabolism
  that produces waste it never processes is a real, if imperfect, fit for the metaphor — worth stating
  exactly this way rather than either fully endorsing or rejecting the label.
- **Adaptation**: applies to targeting, not to outcomes (§6).
- **Environmental interaction**: applies well — real autonomous fetch, real curiosity-driven questions,
  real cross-machine (Echo↔Air) traffic confirmed live tonight.
- **Self-maintenance**: applies well — Liveness Ledger + janitor + log retention are real, demonstrated,
  self-triggered repair/hygiene mechanisms.
- **Reproduction**: **does not apply, and should not be claimed.** No mechanism creates a persistent
  successor or copy with inherited characteristics — self-edit modifies the running instance in place.
  Stated plainly per this document's own instruction not to force categories that don't fit.

**Net assessment: the metaphor is technically useful for five of seven properties and should be
presented with that precision — not asserted wholesale, not dismissed wholesale.**

## 8. System / Model / Emergent Capability Separation

- **Model capability alone**: raw Ollama models, queried directly, solve the large majority of the real
  coding tasks tested in this session's earlier capability-ceiling research (`[inherited]`, ~95-96%
  across independent attempts). This is Echo's underlying LLMs, not FeralEcho-the-system.
- **System capability, real and distinct from the model**: the RiverBrain-driven model-selection loop
  (§2, §4) is a genuine system-level effect — a stateless call to any one of these models cannot
  reproduce "which model gets picked shifts based on 171,000+ real accumulated observations." The
  Liveness Ledger and the recovery/watchdog mechanism are also purely system-level — no LLM call
  produces either.
- **Emergent interaction capability, weaker than hoped**: the intended `memory → retrieval → model →
  evaluation → self-edit → persistence → later retrieval` loop is the strongest *candidate* for a
  genuinely emergent, multi-subsystem capability unavailable from any single call — but §2/§4/§5
  together establish that its evaluation link is broken (AST-only, disconnected from truth), so the
  loop as currently built does not yet demonstrate emergent value beyond what the model-selection
  sub-loop alone already provides.
- **A negative example, worth stating precisely**: `[inherited: Finding 87]` found that self-edit's own
  generation *framing* measurably *hurt* general coding-task performance relative to a raw single-model
  baseline, before the synthesis refactor partially addressed it. This is a case where system-level
  involvement was a net capability *cost*, not a benefit — the opposite of what "emergent capability"
  implies, and worth including precisely because the mission asked not to force examples in only one
  direction.

## 9. Self-Modification Maturity Assessment

Tracing the full chain the mission specifies:

`candidate generation` → `static evaluation (F1)` → `sandbox import test (F2)` → `AST-only deploy gate`
→ `deploy or reject` → `outcome logged` → `future targeting`

- **Code generation**: real, works, produces syntactically valid Python most of the time.
- **Code modification**: real, targeted at specific files, respects `EDIT_FORBIDDEN_TARGETS`.
- **Self-testing**: **partial, and this is the precise place information is lost.** F1 (static safety
  scan) and F2 (import test) are real and correctly enforced. Neither tests whether the code *works*.
  `functional_quality.py` — the one component that could — exists and is validated but disconnected
  (§5). The deploy gate (§4/Findings-91-93's own independent confirmation) compares AST complexity
  scores, which Findings-91-93's own fresh correlation analysis measured at r=0.206 against real
  functional correctness — weak, not statistically significant at n=24, and directly contradicted by
  the single highest-complexity file in the entire corpus, which is functionally broken.
- **Self-correction**: **not demonstrated** — every real fix found or made tonight was made by an
  external investigator (this session, or an earlier Claude Code session), never by Echo detecting and
  repairing her own self-edit failure autonomously.
- **Self-improvement**: **not demonstrated, and one line of evidence actively argues against it** — real
  tracked outcome deltas (`[inherited]`) show no statistically significant mean improvement and a real
  41% negative-outcome rate.

**Precise classification, per the mission's own required distinction: FeralEcho currently has real code
generation and code modification, partial self-testing (safety-complete, correctness-blind), and no
demonstrated self-correction or self-improvement.** This is a materially more conservative and more
defensible characterization than "Echo can edit her own code," which remains true but invites exactly
the overclaim this whole mission exists to prevent.

## 11. Highest-Leverage Closed-Loop Opportunity

The `observe → remember → reason → act → evaluate → learn → change future behavior` loop **exists in
one place, fully closed and proven**: conversational model selection (§2, §4's first two rows). It
**exists but is broken at exactly one step** in the more interesting case, self-edit: `evaluate` reads
an AST-only proxy instead of `functional_quality.py`'s real execution result, which already exists,
already runs, and was already adversarially characterized.

**The smallest architecture capable of closing this loop safely is not a new system — it is two
specific, already-identified fixes to existing code** (§5's `blocked_write` inversion and
`verified_success` gaming), followed by wiring `functional_quality.py`'s output into `RiverBrain.learn()`
and the deploy gate for the `self_edit_coding`/`echo_projects_coding` buckets specifically — not
touching the conversational buckets, which already have a working (if imperfect) loop. **This document
does not implement this** — per its own governing instruction, this is identification, not
authorization.

## 11b. Late Addition — Real Security Finding From the Now-Completed Adversarial Pass

The system-wide adversarial attack pass (`audits/2026-09-06_27day_phase6_adversarial_attack.md`,
completed after most of this document was drafted) found one finding serious enough to record here
directly rather than leave buried in a sibling report: **the F2 sandbox's threat model covers writes
and network, not reads or environment.** Independently re-confirmed in this synthesis pass by direct
grep: none of the four `subprocess.run()` call sites in `functional_quality.py`/`self_edit_manager.py`
pass `env=`, so every sandboxed subprocess inherits the full parent environment by default —
confirmed, `run.py:85` reads `GREMLIN_SECRET` from that same environment. Environment-variable reads
are not intercepted by the sandbox's existing write-guard patches. This is a real, non-hypothetical
credential-exposure path (an `apply_to_code`-shaped candidate returning `os.environ.get(...)` as part
of its output string), not a theoretical one. **This should be treated as at least Tier 0/1 priority
alongside — arguably ahead of — the reward-signal fix in §17**, since it's a real security gap rather
than a capability-ceiling one. Not fixed in this pass; flagged for explicit review, same discipline as
everything else in this document.

The same pass also live-tested self-knowledge confabulation with a genuinely novel, fabricated term
("Tier-3 Consensus Verification Layer") and found Echo produced a confident, structured, fully
fictional five-step explanation with no hedge — a real gap beyond what Finding 43's existing mitigations
were shown to cover, since those were tested against different, already-known false claims, not
novel invented terminology. Three other attacks in the same pass (autonomous-loop staleness,
council same-model exclusion, and the production server's `HF_HUB_OFFLINE` guard) found genuine
containment/correctness holding — stated here for balance, not just the failures.

## 12. Largest Current Capability Bottleneck

**The self-edit/RiverBrain reward signal.** Not "learning is disconnected" in the abstract — precisely:

answer to *"if we could substantially improve only one thing, what should it be?"*

## 13. Strongest Existing Capability

**Recovery**, on the strength of a real, non-simulated incident this same session, correctly handled
end-to-end by pre-existing infrastructure with no ad hoc intervention beyond the documented recovery
procedure. Closely followed by **self-observation** (the Liveness Ledger's real, repeated, multi-month
track record of catching exactly the "looks wired, isn't" failure class this whole mission is worried
about) — arguably the more *strategically* important of the two, since it is the mechanism that makes

## 14. Weakest Critical Subsystem

The self-edit deploy/reward pipeline (§4, §9, §12) — not because it is unsafe (F1/F2/F3 hold, verified
repeatedly and adversarially tonight), but because it is the one place this system claims to be doing
something it cannot currently demonstrate: improving itself.

## FINAL JUDGMENT

**1. What FeralEcho demonstrably is today**: a real, continuously-operating, predominantly local
multi-model orchestration system with genuine cross-session persistence, a real and recently-exercised
recovery capability, and a large, historically-effective self-observation apparatus. Its model-selection
mechanism genuinely, demonstrably adapts based on real accumulated signal. Its self-edit subsystem
generates and safety-tests code changes to itself, targeting real, adaptively-identified weak areas.

**2. What FeralEcho demonstrably is NOT**: a system with a closed, verified self-improvement loop. The
two signals that could make self-edit's evaluation step truthful — real execution outcomes, real human
judgment — are computed and then structurally discarded before they reach any decision. It is not
verified to "remember and be measurably shaped by" specific past experience on the one path directly
tested for this tonight (Finding 76's null result). It does not autonomously detect and correct its own
failures — every correction found tonight came from an external investigator.

**3. The strongest capability we can defend**: recovery, proven by a real incident this session, and
self-observation, proven by a real, repeated, multi-month catch record — both are genuine system
properties, independent of any single model's capability, and neither requires interpretive generosity
to defend in front of a hostile reviewer.

**4. The largest bottleneck preventing the next level**: the self-edit reward signal is blind to
functional correctness, and the two real ground-truth signals that could fix this are already computed,
already persisted, and already going nowhere — this is a wiring problem with a known, bounded fix, not
an unsolved research question, which makes it the single most tractable high-leverage target identified
in this entire investigation.

**5. The single highest-leverage thing to attempt in the remaining 27 days**: fix `functional_quality.py`'s
two adversarially-proven defects, then close the loop it was built to close — wiring real execution
outcomes and real human judgment into the model-selection signal for the self-edit buckets specifically
— and then *measure*, with a real prospective trial designed around this session's own already-discovered
Ollama-concurrency-contention constraint, whether that closure actually produces better outcomes. Not
because it will make the best demo. Because it is the one change that would let this document's own
central finding — "the loop looks closed and isn't" — become, honestly, false.
