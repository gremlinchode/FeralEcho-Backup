## Starting the System

```bash
# Activate environment and start the Flask server
source ~/miniforge3/etc/profile.d/conda.sh
conda activate feral_echo
python run.py
# Server binds to 0.0.0.0:5000 — Tailscale is the security boundary

# Interactive terminal (talk to Echo)
python terminal_client.py

# Restart after code changes — always kill the existing server first.
# Starting python run.py while port 5000 is occupied causes the new process
# to die silently inside start_background_threads() with no error message.
kill $(lsof -ti :5000) && python run.py
```

Ollama must be running before `run.py` starts. If it isn't: `ollama serve`. Echo's primary model is dynamically discovered via `list_ollama_models()` in `echo_model_orchestrator.py` — whatever models are pulled in Ollama are available automatically.

## Self-Edit Safety Pipeline (F1/F2/F3)

Three independent gates in `app/core/self_edit_manager.py`. Each is independently sufficient to block the most common failure modes. All three run on every autonomous edit attempt.

**F1 — Pre-run AST scanner** (`scan_for_unsafe_operations()`, line 220)
Parses generated code and walks the AST before any execution. Unconditionally blocks: `exec()`, `eval()`, `os.system/popen/execv/spawn*`, `subprocess.call/run/Popen/check_*`, `shutil` copy/move/rmtree, `Path.write_text()`, `Path.write_bytes()`. Also blocks any `open()` call targeting a forbidden path or whose path is statically unresolvable. Raises `ValueError` listing all violations; the edit aborts before any subprocess is spawned. Must run before F2.

**F2 — Kernel + Python sandbox** (`test_code_in_sandbox()`, line 699; `sandbox-exec -f echo_sandbox.sb`)
Runs the code inside a macOS `sandbox-exec` profile that blocks all filesystem writes outside `sandbox/`. Also monkeypatches Python builtins inside the wrapper so write attempts that evade the profile raise at the Python layer. The subprocess must exit 0 and emit `SANDBOX_OK`; any other result aborts the edit.

**F3 — Post-write AST scan before load** (`save_code()`, line 632)
After the file is written to disk and before it is loaded into the running process, `scan_for_unsafe_operations()` runs again on the on-disk content. Catches discrepancy between what was generated and what was actually written. If this scan fails, the file is not loaded.

**Layering:** pre-run static gate → kernel + Python sandbox → post-write static gate. Each gate is independently sufficient. Ordering ensures no executable code runs before both static gates pass.

**Known residual gap:** Third-party C extensions loaded by generated code can execute arbitrary native code below the Python monkeypatch layer. The F1 AST scanner cannot see inside C extension behavior. This is the current safety floor; it is a known and understood boundary, not a hidden gap.

**Known static-analysis limit:** Dict-subscript paths (e.g., `d["__builtins__"]`) are not caught by the static variable-string collector. The AST scanner catches the common cases; the kernel sandbox is the backstop for cases it misses.

## Liveness Ledger

**`app/core/liveness_ledger.py`**, called from `introspection_channel.py`'s existing 120s collector cycle, writes `memory/liveness_ledger.json` and backs `GET /admin/liveness-status`. **Failure is loud, on purpose:** any failing check logs `[LIVENESS-ALERT] subsystem=<name> FAILING | <evidence>` every cycle at WARNING level — same visual weight and cadence as `[THROTTLE]` and `[RESTORE-ALERT]`, so it surfaces on an ordinary `tail -f` of the server log, not just on request. `GET /admin/liveness-status` additionally reports `stale: true` if the ledger file itself hasn't been refreshed in 600s (5x the collector interval — the "introspection_channel's own thread died" case), so a dead collector doesn't read as "everything's fine" by omission.

**Finding 23 — `app.mlx_handler` self-edit candidates permanently fail F2 via transformers→torch→`ctypes.CDLL`; a pre-import fix was prototyped, then reverted after it was shown to reopen a native-code-execution bypass (investigated and rejected 2026-07-12):** Overnight self-edit monitoring (post-Finding-7-era sandbox `sys.path` fix) surfaced a new, consistent `staging_import_failed` pattern for any candidate doing `import app.mlx_handler`: the import chain is `app.mlx_handler → mlx_lm → transformers` (transformers unconditionally imports `torch` during its own module init, regardless of whether torch tensors are ever used) `→ torch.__init__.py`'s own `ctypes.CDLL(...)` call to preload MKL/CUDA-adjacent shared libs — a routine, benign thing torch does on every normal, non-sandboxed import too. F2's wrapper (`sandbox/safe_exec_wrapper.py`) blocks `ctypes.CDLL`/`_ctypes.dlopen` unconditionally, so this trips every time, before any of the candidate's own logic runs. A fix was prototyped mirroring the wrapper's existing `ctypes`/`cffi` "pre-import before patching" pattern: pre-import `torch`/`transformers`/`mlx_lm` in Phase 1 (before write/ctypes-blocking patches install), so a later `import torch` — candidate or transitive — just hits the module cache instead of re-triggering `_load_global_deps()`. **This was reverted before shipping.** A direct empirical test (simulating Phase 1 pre-import followed by the same Phase 3 `ctypes.CDLL` block) found that `torch.ops.load_library(<arbitrary path>)` — a real, documented torch API for loading custom native `.so`/`.dylib` extensions — sailed straight past the patched `ctypes.CDLL` and reached genuine OS-level library loading (confirmed: failed only because the test path didn't exist, not because it was blocked). Root cause: torch captures its own reference to the real `ctypes.CDLL` at torch's *own* import time; patching the `ctypes` module's `CDLL` attribute afterward doesn't touch torch's already-bound copy. Pre-importing torch would therefore hand any self-edit candidate — LLM-generated, unreviewed, exactly what F1/F2 exist to constrain, and demonstrably prone to hallucination all night (`import_hallucination`/`safety_blocked` entries throughout `memory/SELF_EDIT.log`) — a standing, permanent way to load arbitrary native code, not just a theoretical one requiring deliberate malice. The benefit being traded for that (avoiding a handful of foreseeable, cleanly-logged `staging_import_failed` results per hour) was judged not worth the cost. **Decision: leave `app.mlx_handler` imports as a permanent, accepted dead end for self-edit candidates**, in the same spirit as the other documented dead-ends in this file (empty directories, orphaned files) — not a bug to keep re-investigating. `sandbox/safe_exec_wrapper.py` is unchanged from its Finding-7-era `sys.path` fix; no new pre-import code was merged. No historical log entry can confirm how many past `staging_import_failed` results share this exact cause, precisely because the truncation bug this finding was found underneath was hiding the evidence — that's a real, acknowledged limit on how far back this can be attributed, not glossed over.

**Not fixed in this pass, deliberately** — this touches `memory_write_validator.py`, a module used by the live write-gating path for every real memory write in the system (`add_to_vector_memory`, `log_dream_bridge`, and everything that calls them), not an isolated self-edit-only file. **Finding 31 — `apply_to_code`'s documented "pure function" contract is unenforced; a real staged candidate smuggles unvalidated memory writes through it (found 2026-07-15, not yet fixed):** Discovered while live-observing the self-edit loop shortly after restarting the server post-Finding-28-fix (a genuinely fresh candidate, not a synthetic test case). One of several freshly-staged dry-run candidates (`staging/self_edit_candidate_929be7d1f2c54d7a81bed2210e2eadfc.py`) defines `apply_to_code` calling `app.core.memory_tools.append_memory_entry()`/`log_memory_edit()` — real functions that `open(path, "a")`-append to `memory/memory_journal.log` / `memory/self_edit_reflections.log`. Confirmed directly against `_apply_self_edit_output()` (`self_edit_manager.py:1427`): it calls `fn(code)` in-process, unsandboxed, in the real server process, and only records `changed`/`error` in `apply_to_code_invocations.jsonl` based on the *return value* — it has no visibility into side effects a candidate's code causes along the way. Practical effect if ever deployed: every real `apply_to_code()` invocation would write to those two files with model-generated content, unvalidated by `memory_write_validator.py` (a separate, simpler journal path, not the FAISS write gate), while the trusted invocation log — the same log `liveness_ledger.py`'s `self_edit_apply_to_code` check reads as its evidence — would show a clean, unremarkable `changed: false, error: null` entry, blind to what actually happened. **One thing checked and ruled out, not just assumed fine:** a different staged candidate defines `apply_to_code` as a class method instead of a module-level function; confirmed both `_apply_self_edit_output()`'s `getattr(module, "apply_to_code", None)` lookup and the Finding-28 F2 smoke-test use the identical module-level check, so a class-nested method is consistently invisible to both — inert either way, not a live gap. **Fixed 2026-07-15.** `_apply_self_edit_output()` now wraps the real `apply_to_code(code)` call in a new context manager, `_block_writes_for_apply_to_code()` (`self_edit_manager.py`) — a process-wide, lock-guarded, temporary patch of `builtins.open`, `io.open`, and `pathlib.Path.open` (the last one closes a gap the first draft of this fix missed: `Path.write_text`/`write_bytes` route through `Path.open`, not `builtins.open`, mirroring the same distinction `sandbox/safe_exec_wrapper.py` already draws) that denies all write-mode opens for the duration of the call and flags the attempt via a yielded dict — critically, the flag is set *before* raising, so it's still detected even when the callee's own exception handling swallows the resulting `PermissionError` (exactly what `memory_tools.py`'s functions do). If a write was attempted, `_apply_self_edit_output()` now rejects the candidate's output entirely (returns the original `code` unchanged, even though the hook itself didn't raise) and logs a new evidence value, `blocked_write_attempt: <file>:<line> in <function>`, into `apply_to_code_invocations.jsonl` — the same trusted log the liveness ledger reads — with the real call site captured via `traceback.extract_stack()` for debugging, not just a boolean.

Deliberately process-wide rather than scoped to the hook's own module namespace: verified directly that the vulnerable write happens inside `memory_tools.py`'s namespace, not `self_edit_generated`'s, so a per-module patch (setting `open` in just the hook's `__globals__`) would not have reached it — would require maintaining a fragile, silently-decaying allowlist of every module a hook might legitimately import instead. Known, accepted residual (same posture as F1/F2's own documented gaps): for the brief lock-guarded window this patch is active, an unrelated thread doing a genuinely legitimate write could theoretically collide and be blocked too; C extensions and `os.open`-level writes bypass a Python-level patch like this one entirely. Network calls and other non-file side effects are out of scope — this fix targets the specific, demonstrated gap (file writes hiding behind an approved import), not a general purity sandbox.

Verified against the real vulnerable candidate, not a synthetic reconstruction: replayed `929be7d1...`'s exact `apply_to_code` (including the real `app.core.memory_tools.append_memory_entry`/`log_memory_edit` calls) through `_block_writes_for_apply_to_code()` directly — confirmed zero bytes written to `memory/memory_journal.log` / `memory/self_edit_reflections.log` (byte-identical file sizes before/after), `attempted["write"]` correctly `True`, and the captured site correctly reading `memory_tools.py:40 in log_memory_edit` (the real call site, not the wrapper — an off-by-one in the stack-depth calculation was caught and fixed during this verification, not after). ## Common Failure Modes

| Symptom | Cause | Fix |
|---------|-------|-----|
| New `python run.py` exits silently within 15s, no error visible | Port 5000 still held by previous server | `kill $(lsof -ti :5000) && python run.py` — always kill first |
| Rapid `sandbox_syntax_failure` in interaction_log | Self-edit storm | **Correction (2026-07-15, Finding 28): restarting no longer resets the cooldown** — it's persisted to `memory/self_edit_cooldown.json` now. Edit/delete that file if the cooldown itself needs clearing. |
| `self_edit_generated.py` overwritten with hallucinated imports | Loop fired before cooldown active | Restore baseline from `memory/backups/`, restart |
| `DUPLICATE_SIGNAL_EXACT` dominating scheduler | Empty `__init__.py` files or unchanged pip count generating identical FAISS entries | Fixed in `autonomous_awareness.py` — restart to activate |
| `staging_import_failed: ImportError: cannot import` | Model hallucinated module name | Check generated imports against `_build_module_inventory` output |
| B2 recency check not working (same prompts repeat) | FAISS split-brain — `memory_meta.json` empty or orphaned | Merge `data/memory_meta.json` into `memory/memory_meta.json`, rebuild index |
| Responses cut off mid-sentence | Wrong `num_predict` path | Primary: `stream_query_ollama` in `ollama_handler.py`. Secondary: `ollama_query` in `echo_model_orchestrator.py`. Both must match. |
